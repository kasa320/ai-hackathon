# 適応型Personal Ops Agent

- 作成日: 2026-09-19
- 状態: 有力候補・要スコープ決定
- 出発点: `/home/kasa/src/personal/secretary-bot/`

## 一言で表す

> 計画を立てるだけでなく、計画が崩れた理由を学び、明日から現実的な計画へ自動で立て直す個人秘書エージェント。

## なぜ有力か

- すでに本人が実利用しているため、架空の課題ではない
- 定期起動、情報収集、計画、Calendar／Tasks操作、結果検証、記憶更新まで一周している
- 「持ち越しを翌日に積む」という一般的なタスク管理の失敗を具体的に解決している
- 実際の失敗例と改善規則が蓄積されており、Before／Afterを作りやすい
- 予定が崩れる瞬間は短いデモでも理解しやすい

## そのままでは弱い点

- 「AIがタスクをカレンダーへ自動配置する」だけならMotion、Reclaim、Trevor AI、SkedPalなどと競合する
- Notion Custom Agentsも、指定した知識ベースを読み、定期実行し、Calendarを最適化・更新できるため、「自分のノートに基づく予定管理」だけでは差別化できない
- cronから長いプロンプトを実行するだけに見えると、技術力を評価されにくい
- 個人専用ルールが多く、他人にも使えるプロダクトに見えにくい
- 実データを発表に使うと、個人情報を露出する危険がある
- 何をもって計画が改善したかの評価指標がまだ明示されていない

## 推奨する切り口

### 第一案: 計画復旧エージェント

「予定を作る」よりも「崩れた計画を立て直す」に絞る。

#### 課題

一般的なタスク管理は、未完了タスクを翌日へ送る。その結果、翌日がさらに過密になり、計画が雪だるま式に破綻する。また、未完了だけを見て本人の怠慢や能力不足と判断すると、誤った計画学習になる。

#### 解決

1. 期限超過や予定変更を検知する
2. 本人の短い説明、予定、完了実績から原因を分類する
3. 固定予定と締切を保護したまま、影響範囲全体を再計画する
4. 変更案と理由を提示し、必要な操作だけ承認を求める
5. 結果をCalendar／Tasksへ反映する
6. 見積もり・一日容量・配分規則を次回へ引き継ぐ

#### 独自性の核

スケジュール最適化そのものではなく、**計画失敗の原因を誤帰属せず、説明可能な記憶として次回へ反映すること**。

### 第二案: 学生向けLifeOps

大学生活に対象を絞り、シラバス、課題、授業、移動、資格学習、復習記録を横断する。

強みは当事者性と原資料からのタスク生成。弱みは支払意思を示しづらいこと。学生本人向けB2Cだけでなく、学習継続・離脱防止を支援する大学向けという将来像も考えられるが、MVPでは広げすぎない。

### 第三案: 汎用Personal Ops

仕事、学習、生活をまとめる個人秘書として見せる。市場は広いが、競合との差を短いピッチで伝えにくいため、今回の第一選択にはしない。

## 推奨デモ

実データではなく、架空ユーザーの一週間を使う。

### 初期状態

- 明日までの課題、継続学習、固定された授業・通院・移動がある
- 既存計画は容量ぎりぎり
- 前日に二つのタスクが未完了

### デモの流れ

1. エージェントが未完了を検知する
2. 「急な予定が入り、学習できなかった」という情報から外的要因と判定する
3. 本人の作業速度を下げず、その週だけ利用可能容量を減らす
4. 未完了を翌日へ単純加算せず、固定予定と外部締切を守って一週間を再配置する
5. 日課の一時停止や低優先タスクの延期を提案する
6. 変更前後、判断理由、保護した制約を画面に表示する
7. 承認後にCalendar／Tasksへ反映する
8. 翌回、同じ条件では最初から過密にしないことを示す

## デモ画面で見せる情報

- 左: 変更前のカレンダーと期限超過タスク
- 中央: エージェントの原因判定、制約、実行計画
- 右: 変更後のカレンダー
- 下部: `提案のみ`、`承認待ち`、`反映済み`、`反映失敗`の監査ログ

## 技術構成案

```text
定期・イベントトリガー
  -> Context Collector
     Calendar / Tasks / 原資料 / 個人ルール / 過去実績
  -> Planner
     LLMによる意味理解・原因分類
     制約充足ロジックによる時間配置
  -> Policy & Approval
     固定予定、他人が関わる予定、外部締切、購入等を保護
  -> Executor
     Calendar / Tasksへ反映
  -> Verifier
     再取得して衝突・重複・未反映を検査
  -> Calibration Memory
     観測、原因、調整、次回規則を保存
```

LLMだけに時刻計算を任せず、意味理解と原因分類をLLM、重複のない配置を決定論的な制約ロジックに分けると、技術力と信頼性を示しやすい。

## 評価指標候補

- 計画作成・立て直しにかかる人間の時間
- 再計画後の予定衝突数
- 一日の予定容量超過時間
- 期限超過タスクの単純翌日送り件数
- 予測所要時間と実績の誤差
- エージェントが提案した変更の承認率
- 変更理由をユーザーが理解・納得できた割合

## ピッチ案

> 予定を立てるAIは、すでにあります。しかし現実の計画は必ず崩れます。既存のタスク管理は、終わらなかった仕事を明日へ積み上げ、さらに実行不能な一日を作ります。このエージェントは、なぜ計画が崩れたかを理解し、あなたを責めずに、計画のほうを学習させます。
