# 輪読運営エージェント：実現性と受賞を狙うための検討

検討日：2026-09-19。企画・設計案であり、実装・ユーザー検証・費用計測は未実施。採用確定の仕様ではない。

## 1. 現時点の判断

**開発候補として推奨。ただし「日程調整と催促をするAI幹事」だけでは、最優秀賞を狙うには弱い。**

中心に置く価値は、技術書の輪読で準備不足や欠席が発生したとき、参加者の条件とグループの方針から、次回の範囲・担当・進め方を組み直し、必要な合意を集めて反映すること。

仮の一文説明：

> 参加者は近況に答えるだけ。準備状況が変わっても、AIが次の輪読を開催できる状態に整える。

学習そのものや人間同士の議論は参加者が担う。AIが担当するのは、状況確認・調整・合意の回収・運営情報の更新・結果確認という運営業務。

## 2. 確認した事実と、まだ分からないこと

### 確認したこと

- 本人に技術書の輪読参加経験があり、準備・演習・発表担当・開催日時の変更に関する記録がある。
- 今回の公式資料では、セキュリティ、コストパフォーマンス、信頼性・堅牢性、自律性、アイデア・独創性が各10点。
- 最終提出は9/22 15:00。ソースコードとQiita／Zenn記事が必要。決勝は発表4分・質疑3分。

### 未確認のこと

- 幹事や参加者が、何にどのくらい負担を感じているか。
- 参加者が短い進捗確認に回答するか、AIからの調整を受け入れるか。
- 普段の連絡手段、開発人数、実際に確保できる開発時間。
- 既存製品すべてとの差別化、有料利用への意向、長期継続への効果。

本人の個人スケジュールの難しさは、輪読会全体の運営負担を直接証明しない。ここはヒアリングで確かめる。

## 3. 競合を踏まえた位置づけ

以下は各社の公式ページに記載された機能の確認。実機での利用検証や全機能の網羅調査ではない。

| サービス | 公式ページで確認した機能 | この企画への示唆 |
| --- | --- | --- |
| [Bookclubs](https://bookclubs.com/) | 日程、投票、出欠、通知、メッセージ、読書履歴 | 輪読の運営情報を一か所に集めるだけでは新しくない |
| [Readfeed](https://www.readfeed.com/) | ビデオ会議、予定、出欠、通知、AIによる議論の問い・章の質問 | 「読書会にAIを付けた」だけでも差が弱い |
| [Lapwing Book Club](https://bookclub.wiselapwing.co.uk/) | 予定調整、投票、AIの推薦・議論用質問 | 日程調整と質問生成をまとめるだけでは不足 |
| [Doodle](https://help.doodle.com/en/articles/9457379-how-do-automatic-reminders-for-group-poll-work) | 未回答者への自動リマインド | 催促だけはAIの必然性が薄い |

上記ページでは「準備状況や担当者の変更を受けて、技術書の扱う範囲と開催形式を再構成し、合意・更新まで進める」という一連の機能は確認できなかった。ただし、機能が存在しないと断定するものではない。

差別化の仮説は、**予定や回答を管理する機能から、次回を成立させる調整の実行へ進むこと**。

## 4. 具体的な利用場面

4人、週1回60分、技術書を章や節に分けて読む輪読を仮定する。

事前に共有したルール：

- 原則として開催日時は固定。
- 担当変更は本人の引き受けが必要。
- 範囲の縮小や復習回への変更には、グループが設定した同意条件を適用。
- 日時変更・中止は主催者の判断が必要。
- 返事がないことを賛成として扱わない。
- 個人的な事情は共有しない。

開催前に、発表担当Aが「今回は担当できない」と報告する。Bは「前の節の○○がまだ曖昧」、Cは「第2節なら15分説明できる」、Dは「予定どおり参加できる」と回答する。

AIはこの条件を整理し、必要ならCに引き受け意思を確認する。全範囲の発表を維持する案と、扱う範囲を絞る案を検討し、後者なら開催可能だと判断する。

「Cの説明15分、前の節の確認20分、第2節の議論25分。残りは次回へ」という案を作り、必要な人に確認する。同意条件を満たすと、担当・進行表・次回の範囲・参加者への通知を更新する。

同じ状況でもCが引き受けない場合は、同じ案を押し通さず、発表者なしの共同読解がルール上可能か検討する。成立しなければ、選択肢と未解決点を主催者へ返す。

**完了条件は、提案文ができたことではない。必要な同意が揃い、実施可能な担当と進行表が保存され、通知状況を確認できたこと。**

## 5. なぜ専用サービスにするのか

汎用エージェントにも同様の推論は依頼できる。本案の価値はモデル固有の能力ではなく、次の仕組みを利用者が組み立てずに使えることにある。

- メンバーごとに参加し、自分の状態と意思を入力できる。
- 個人の事情と、グループで使う情報を分ける。
- どの案に誰が同意したかを、変更版ごとに保持する。
- 返信や期限をきっかけに、自動で調整を再開する。
- 確定した担当・範囲・予定の正本が一つあり、全員が確認できる。
- 変更の重複、古い案の確定、他人の同意の捏造を防ぐ。

単にチャット画面を作るだけでは、この価値は実現しない。

## 6. AIと通常のプログラムの分担

| AIに任せること | コードで保証すること |
| --- | --- |
| 「参加できるが発表は難しい」などの意味を整理 | 投稿者の認証と、所属グループ・操作権限 |
| 不足している情報と、聞く相手を選ぶ | 未回答を同意として扱わない |
| 参加条件や質問内容から、進め方の案を作る | 時間の合計、重複、担当者の引き受け条件 |
| 断られた結果から、別の案を検討する | 同意を案の版に結びつけ、変更時に再判定 |
| 共有してよい情報を使って説明を作る | 個人の原文を共有用モデル・公開APIに渡さない |
| 次に呼ぶ業務ツールを選ぶ | 変更の保存、通知の再試行、予算と実行回数の上限 |

曖昧な情報から、本人の意思や理解度を確定しない。入力の解釈を本人が修正できるようにする。自律性は、必要な人間の意思決定を省くことではなく、判断済みの範囲の調整をAIが進めることで示す。

## 7. 実装構成

最初はWebアプリと単一のエージェントで作る。参加者の数だけLLMエージェントを増やす必要はない。

### 画面は3種類

1. **参加者の画面**：今回の範囲、出欠・準備状況の入力、自分への確認、引き受け／辞退。
2. **輪読会の共有画面**：次回の日時・担当・進行、確定事項、未解決の調整。
3. **主催者の画面**：任せる範囲の設定、判断が必要な案件、実行履歴・費用。

開発用の人物切り替え画面と、本番の認証・権限検証は区別する。URLやリクエストのメンバーIDを書き換えるだけで他人になれる作りにはしない。

### サーバーの処理

1. 投稿・ボタン操作・開催前の期限到達をイベントとして保存する。
2. 対象の回の最新状態を読み、エージェントが次の行動を選ぶ。
3. ツール実行前に権限、グループのルール、情報の鮮度を検証する。
4. 返信待ちなら状態を保存して終了する。待っている間はLLMを回さない。
5. 返信で再開し、条件を満たした変更を保存して通知する。

状態は「情報収集中／案を作成中／同意待ち／反映待ち／確定／主催者の判断待ち」などでDBに保持する。

### 最小限の業務ツール

- 今回の参加条件・準備状況・過去の担当履歴を取得する。
- 特定の参加者へ、回答期限付きの確認を出す。
- 範囲・担当・進行の変更案を保存する。
- 時間と引き受け条件を検査する。
- 必要な同意を求める。
- 同意済みの案を確定し、通知する。

これらをOrcaRouterのツール呼び出しで選択させる。[公式ドキュメント](https://docs.orcarouter.ai/advanced/tool-calling)

DBには、グループ、所属、開催回、節・テーマ、参加条件、変更案と版、同意、未処理イベント、通知キュー、実行ログを持つ。初期実装は慣れた言語で一つのサーバーと一つのDBにまとめる。

### 外部連携

MVPの正本はアプリ内。個人カレンダー全員分への接続を必須にしない。

普段の連絡手段がDiscordなら、ボタンやフォームから回答を受け取る連携を一つ追加する。Discordはこの種のInteractionを提供している。LLM処理の前に受領応答し、処理を非同期に進める必要がある。[Discord公式資料](https://docs.discord.com/developers/interactions/receiving-and-responding)

外部連携が未実装の場合は、そのことを明示する。アプリ内で担当変更・同意・通知が実際に機能することを先に完成させる。

## 8. 自律性と安全性を両立する設計

- **最初に委任ルールを設定**：確認の送信、通知回数、担当交代、範囲変更、日時変更について、条件を決める。
- **新しい負担は本人が引き受ける**：AIが勝手に担当を押し付けない。一度明示された引き受け条件の範囲では再確認を繰り返さない。
- **個人情報を分離**：私的な理由の記入は不要。書かれた場合も、共有するのは本人が確認した参加可否・担当可能範囲など。共有文を作るモデルには私的な原文を渡さない。
- **小人数での推測可能性に注意**：理由を伏せても、担当変更の対象者は分かる。「完全匿名」とは説明しない。
- **負担の偏りを抑える**：連続担当や準備時間の上限をルールとして持ち、いつも同じ人を代役にしない。
- **通知を制限**：未回答者へ一度確認し、期限後は主催者へ戻すなど、催促上限を決める。
- **古い案を確定しない**：案の版と同意を関連付け、状況が変われば必要な同意を取り直す。
- **処理を重複させない**：同じ回答の再送を識別し、通知待ちをDBに保存する。外部送信の成否が不明な場合は未確認として扱い、無条件に再送しない。
- **失敗時は確定情報を維持**：API障害や予算上限で、新しい案を確定したように見せない。

## 9. 最優秀賞を狙うための評価

得点予測や受賞確率は出せない。以下は審査基準に対する設計上の見立て。

| 評価項目 | 現時点の見立て | 狙うべき実証 |
| --- | --- | --- |
| 自律性 | 最も強みにできる | 欠席・準備不足・辞退に応じて手順が変わり、調整結果が実際に反映される |
| セキュリティ | 用途と自然に結びつく | 他人の私的事情を読めない、他人の同意を代行できない、別グループを変更できない |
| 信頼性・堅牢性 | 実装で差がつく | 二重回答、古い同意、モデル障害、通知失敗から整合性を保って復旧する |
| コストパフォーマンス | 測定しやすい | 同じケースで成功率を維持し、調整1件の推論費用と人の操作数を比較する |
| アイデア・独創性 | 現状で最も弱い | 単なる日程調整ではなく、技術書の準備状況に応じた開催の組み直しを示す |

最大の弱点は「人が連絡すればすぐ済む小さな問題ではないか」という反論。実際の会で、誰が何回確認し、どこで調整が止まったかを示す必要がある。

大学の輪読会を入口にし、将来的に社内勉強会や研修へ広げる余地はある。ただし、社内需要や課金意思は未検証。発表では学生向けの実証を軸にし、未確認の市場規模や売上を作らない。

## 10. 最小実装と工数の目安

開発人数と確保時間が未回答のため、1人・合計約26〜38時間を仮置きした概算。保証ではなく、連携設定や経験によって増える。

| 作業 | 目安 |
| --- | ---: |
| 利用場面の確認、委任ルール、デモ条件の固定 | 2〜3時間 |
| 参加者・開催回・変更案・同意の保存と3画面 | 6〜8時間 |
| エージェント、ツール、返信待ちからの再開 | 6〜9時間 |
| 権限・競合・通知失敗への対応 | 4〜6時間 |
| 比較評価と、協力者による一度の試用 | 4〜6時間 |
| 提出記事、説明画面、デモ録画 | 4〜6時間 |

上記はWeb内で完結する最小版。Discordなど外部連携は別途時間が必要。

20時間未満なら、日時は固定し「担当変更と範囲の組み直し」に限定する。複数の連携、会議録音、議事録、教材の全文取り込み、AIによる理解度採点、会議中の音声司会は入れない。

最初の段階で、4人の入力から一つの担当変更を確定し、全員の画面が更新されるところを通す。見栄えや追加機能より先に、成立に必要な流れを完成させる。

## 11. 検証方法

### 利用価値

本人を含む3〜4人に、直近の輪読で実際に困った変更を聞く。同じ条件で、従来の運営と試作品を比較する。

測るのは、主催者が自分で行った確認・転記の回数、実操作時間、参加者の入力負担、最終的な案が受け入れられるか。返信を待つ時間とシステムの処理時間は分ける。

一度の試用で長期継続率の改善までは主張しない。

### 動作と費用

正常、担当欠席、準備不足、代役辞退、未回答、全員都合が合わない、重複送信、古い同意、他人へのなりすまし、私的事情の抽出要求、モデル障害、通知失敗を含む12ケースを用意する。調整に成功することが正解のケースと、安全に停止することが正解のケースを分ける。

正常・変更・辞退などの代表ケースは複数回実行し、偶然一度成功しただけにならないようにする。

高性能モデル固定と、低価格モデル中心・必要時のみ高性能モデルの構成を、同じ入力・ツール・権限・完了条件で比較する。失敗・再試行の費用も含める。

OrcaRouterのNamed Routerで候補を絞り、利用モデルを記録する。少数の試験で自動ルーティングが十分学習したとは主張しない。[Named Routers](https://docs.orcarouter.ai/routing/named-routers)

リクエストIDを保存し、確定した請求額を照合して調整1件の費用に集計する。費用フィールドがない場合を0円としない。サーバー費用は推論費用と区別する。[Per-request cost](https://docs.orcarouter.ai/operations/per-request-cost)

## 12. 4分の発表

- **0:00〜0:30**：実体験。準備状況が変わるたび、幹事が調整を引き受ける。
- **0:30〜1:00**：次回の輪読と、参加者が委任したルールを紹介。
- **1:00〜2:20**：担当者が辞退。AIが代案を作り、別の参加者へ確認。その返答で計画を修正する。
- **2:20〜2:50**：同意が揃い、担当・進行表・通知が実際に更新される。
- **2:50〜3:20**：私的事情が共有されないことと、同じ操作を再送しても二重処理しないことを示す。
- **3:20〜4:00**：試用結果、成功率、実測費用、未対応の範囲を示す。

開催前の定時処理や長い回答待ちは、時刻を進めるデモ機能で短縮し、その旨を明示する。参加者の回答は実際に入力し、LLMの判断やDB更新を録画だけで代用しない。通信トラブル時の予備録画は別途用意する。

## 13. 採用判断の条件

進める条件：実際の参加者が運営上の調整に負担を感じ、簡単な状態入力を受け入れ、担当・範囲の変更をこの仕組みに任せたいと言えること。

見直す条件：困りごとが日程投票だけ、メンバーが状態入力をしない、毎回全操作に幹事の手作業が必要、または作れる時間が安全な最小版に足りない場合。

**受賞を狙うための核は、「次回をどうするかを提案した」ではなく、「参加者の意思を守りながら調整を完了し、幹事の仕事が実際に減った」と示すこと。**
