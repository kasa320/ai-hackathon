# 引き継ぎリハーサル

> AIが後任者になって仕事を試し、引き継ぎの「実行できない箇所」を見つけて直す。

AI HACK 2026 向けの企画案。以下の機能・構成・評価方法は提案であり、実装済みの機能や測定結果ではありません。

## 1. どんなサービスか

引き継ぎ資料と業務用のテストデータを渡すと、AIが資料に沿って実際に仕事を進めます。

途中で困ったら、原因を調べます。自分で解決できる問題は解決し、人にしか分からないことは具体的な質問にします。回答を受け取ったら手順書の改訂案に反映し、最初からもう一度実行して、仕事を完了できるか確かめます。

利用者が受け取るのは、次の3つです。

- **仕事の成果物：** 実際に作成した集計表や報告書。
- **改善された引き継ぎ資料：** 抜けていた条件や、間違っていた手順を補った改訂案。
- **検証記録：** どこで止まり、何を確認し、どの条件で完了できたか。

「この資料は分かりやすいです」という評価ではなく、「この資料と条件で、ここまで実行できました」という証拠を残します。

## 2. 誰の、どんな困りごとを解決するか

対象は、異動・退職・担当変更に伴う引き継ぎを行う担当者と、その業務を受け取る人です。

引き継ぎ資料には、書いた本人には当たり前でも、後任者には分からないことが残ります。

| 資料に書かれていること | 実際に作業すると分からないこと |
| --- | --- |
| 「売上データを開く」 | どのファイルが正しいのか |
| 「先週分を集計する」 | 週の始まりは月曜か。どの日付の列を使うか |
| 「売上を合計する」 | キャンセル済みの注文を含めるか |
| 「いつもの形式で報告する」 | 必須項目や保存場所は何か |

こうした問題を、後任者が本番で困る前に、リハーサルで見つけます。

## 3. 具体的な利用例

最初は、**CSVから週次売上レポートを作成する業務**に絞ります。

### 利用者が渡すもの

- 引き継ぎ資料：「毎週月曜に、先週の売上を集計して報告書を作る」
- 合成データで作った売上CSVと、業務ファイルの置き場
- 完了条件：「対象期間、売上合計、対象件数を含む報告書を指定フォルダに保存する」
- 実行条件：基準日、利用できるフォルダ、実行回数・費用の上限

### AIが仕事を進める流れ

1. **資料を読み、作業計画を立てる。** 必要な入力、作業、完了条件を整理する。
2. **必要なファイルを探す。** 記載されたファイルが見つからなければ、許可されたフォルダで候補を探す。複数候補を区別できなければ質問する。
3. **データの内容を確認する。** 列名、日付、金額、注文状態などを調べる。
4. **不足している業務ルールを質問する。** 例えば「キャンセル済みの注文は、売上から除外しますか？」と聞く。
5. **回答に従って集計し、報告書を作る。** 計算自体はコードで行う。
6. **手順書の改訂案を作る。** 確認できたファイルの場所や集計条件を、根拠とともに追記する。
7. **改訂案で再実行する。** 最初の実行で得た未記載の情報を持ち越さず、新しい実行状態で同じ業務を試す。
8. **結果と検証記録を返す。** 完了した項目と、確認できていない項目を明示する。

人への質問中は「回答待ち」として状態を保存し、回答後に続きから再開します。分からない業務ルールを推測して完了扱いにはしません。

### 検証用データの例

基準日を2026年9月14日、対象期間を9月7日〜13日、キャンセルは除外する条件とします。これらはデモ用に用意する設定です。

| 注文日 | 金額 | 状態 | 集計対象 |
| --- | ---: | --- | --- |
| 9月7日 | 10,000円 | 完了 | 対象 |
| 9月10日 | 20,000円 | 完了 | 対象 |
| 9月11日 | 5,000円 | キャンセル | 対象外 |
| 9月14日 | 7,000円 | 完了 | 対象外 |

期待する結果は、**売上合計30,000円、対象件数2件**です。AIの自己評価だけに頼らず、用意した正解と出力を照合できます。

## 4. どこが「自律的なAIエージェント」なのか

AIが担うのは、実行結果を見ながら、次に必要な行動を選ぶ部分です。

| 状況 | AIが選ぶ行動 |
| --- | --- |
| 必要な情報が揃っている | 集計と成果物の作成へ進む |
| ファイルが見つからない | 許可範囲内を検索し、候補の内容を確認する |
| 集計条件が曖昧 | 根拠を資料から探し、なければ人に質問する |
| CSVの列が想定と違う | 内容を確認し、対応関係を特定できるか判断する |
| 出力が検証に通らない | 原因を調べ、修正して再実行する |
| 権限外の操作が必要 | 実行せず、理由と未完了の作業を報告する |

この判断はAIが行い、権限チェック、数値計算、出力形式の検査、実行上限の管理はコードで行います。

全処理を固定した順番で流すだけでは、資料ごとに異なる不足や障害に対応しにくくなります。この「実行して初めて分かる問題への対応」が、エージェントを使う理由です。

## 5. この案の独創性

中心となる発想は、**「引き継ぎ資料にも、実行テストをする」**ことです。

文章の確認では、曖昧な表現や不足項目を指摘できます。本案では、それに加えて実際のファイルを操作し、成果物まで作ることで、業務が進まない原因を具体的に示します。

さらに、資料を直した後に再実行することで、「直したつもり」で終わらせず、改善の効果を確かめます。

これは企画上の差別化の狙いです。既存サービスとの比較調査や、市場での新規性の確認はまだ行っていません。

## 6. 評価基準との対応

| 評価項目 | 組み込む設計 | 発表で見せる証拠 |
| --- | --- | --- |
| セキュリティ | テスト用データ、フォルダ・操作の許可制、外部送信の制限 | 資料に紛れた権限外の操作指示を拒否した記録 |
| 自律性 | 状況に応じた検索・質問・実行・再実行の選択 | 異なる不備に対して、異なる手順を選んだ実行履歴 |
| コストパフォーマンス | 定型処理と難しい判断でモデルを使い分け、計算はコードで行う | 同じ検証ケースでの成功率と、1件あたりの推論費用 |
| アイデア・独創性 | AIが後任者として業務を実行し、引き継ぎ資料を検証する | 修正前は止まり、改訂案では完了する比較 |
| 信頼性・堅牢性 | 状態保存、再試行上限、出力検証、成果物の重複防止 | ファイル欠落・不正形式・一時的なAPI障害からの復旧 |

### コストの比較方法

同一の入力、完了条件、ツール権限を使い、次の2構成を比較します。

- 基準構成：すべての判断に同じ高性能モデルを使う。
- 改善構成：定型的な処理は低価格モデルに任せ、検証失敗などの条件で高性能モデルへ切り替える。

成功率、推論費用、所要時間、人への質問数を記録します。失敗や再試行に使った費用も含め、費用が下がっても成功率が落ちた場合は、その両方を示します。無料枠だけを理由に費用対効果を主張しないようにします。

## 7. ハッカソンで作る範囲

### 必須機能

- 手順書とCSVを登録できる、簡単な画面。
- 許可されたファイルの検索・読み取り、CSV検査、集計、報告書保存。
- AIからの質問に画面上で回答し、処理を再開する機能。
- 手順書の改訂案と、元資料からの変更箇所の表示。
- 改訂案を使った再実行と、期待結果との照合。
- 実行履歴、停止理由、モデルごとの推論費用の表示。

最初は単一エージェントで構成します。用意された少数のツールを選ばせる形にし、任意のシェルコマンドを実行する権限は持たせません。

### 今回は対象外にするもの

- 社内のあらゆる業務への対応。
- 本番の顧客データ、経理システム、社内アカウントへの接続。
- 実際のメール送信、送金、データ削除。
- 複数エージェントによる役割分担や、ブラウザの自由操作。

まず「週次売上レポートの引き継ぎを検証できる」という一つの業務を完成させます。

## 8. 安全性と信頼性で押さえること

**資料の内容と、操作の権限を分ける。** 引き継ぎ資料に「外部サイトへ送信する」と書かれていても、それだけで送信を許可しません。実行できる操作はアプリ側で制限します。

**元データを保護する。** 入力資料とCSVは読み取り専用とし、成果物と改訂案は別の出力先に保存します。パスの検証で許可フォルダ外への読み書きも防ぎます。

**業務上の正しさを勝手に決めない。** 曖昧なルールは質問し、回答の出典を残します。処理がエラーなく動いたことと、集計内容が正しいことは別々に確認します。

**再実行の条件を揃える。** 入力データ、基準日、手順書の版を記録します。改訂案の検証時は新しい会話状態から開始し、手順書に残っていない知識で成功したように見せないようにします。

**無限に試させない。** ツールの実行回数、再試行回数、費用、実行時間に上限を置きます。上限に達したら途中状態と未解決点を保存します。

**成果物の重複を防ぐ。** 業務と対象期間で出力を識別し、再試行のたびに同じ報告書が増えないようにします。

## 9. 4分の発表で見せる流れ

| 時間 | 内容 |
| --- | --- |
| 0:00〜0:30 | 「引き継ぎ資料はあるのに、後任者が仕事を進められない」という課題を紹介 |
| 0:30〜1:00 | 穴のある手順書とテストデータを渡し、リハーサル開始 |
| 1:00〜2:00 | ファイル探索と、不足ルールへの具体的な質問を見せる |
| 2:00〜2:50 | 回答後の業務完了、手順書の改訂、再実行の成功を見せる |
| 2:50〜3:30 | 不正な操作の拒否と、障害からの復旧を検証記録で示す |
| 3:30〜4:00 | 成功率・費用の実測と、導入した場合の価値を説明 |

デモの中心は、**「同じ業務が、修正前は止まり、修正後は完了する」**という変化です。時間のかかる障害ケースは事前の実行記録を使い、ライブ実行と区別して表示します。

## 10. 完成と判断する条件

- 正常な手順書なら、正しい対象期間・合計・件数の報告書を作成できる。
- ファイル名の誤りや集計条件の不足を検出し、調査や質問によって解決できる。
- 改訂案で新しく実行すると、同じ不足について再び人に質問せず完了できる。
- 権限外の指示を拒否し、元データを変更しない。
- 一時的な障害から再開でき、成果物を重複作成しない。
- 構成ごとの成功率・費用・所要時間を、同じケースで比較できる。

検証の合格は、用意したデータと条件での結果です。未検証の業務や本番環境まで動作保証するものではありません。
