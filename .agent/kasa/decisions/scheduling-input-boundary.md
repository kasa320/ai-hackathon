# 日程調整の参加方針と入力境界

記録日：2026-09-21。関連：[現在の日程実装](schedule-by-agent.md)、[Discord対話](discord-interactive-agent.md)。

## 決定事項

- ユーザーとの壁打ちで、日程調整の初期設定は全員参加を優先すると確認した。
- 理由：輪読を全員で進める前提で、合わない回の日時・所要時間・進め方を調整するため。
- 初期設定として、参加人数を最大化して欠席者がいるまま確定する方式は採らない。全員参加を必須条件にする範囲や、例外の承認方法は今後具体化する。

## 検討中の提案（実装・公開APIの変更は未実施）

ユーザーから、Discordの自由文を特定パラメータの抽出に限定し、原文を計画側へ渡さない設計が提案された。

- 抽出用LLMは本人の回答の下書きだけを返す。認証情報・対象の会・質問・案の版はアプリが束縛する。
- 型・列挙値・日時・対象範囲・整合性を検証し、本人が確認した構造化情報だけを計画側へ渡す。
- 可否・時間帯・所要時間などは限定した型にし、自由記述の理由や要約を後段へ渡す抜け道を作らない。
- 承認・担当の引き受けは本人の明示操作で記録し、抽出LLMの出力から作成しない。
- 候補日の可否はボタンで直接入力可能にし、自由文からの抽出には確認を挟む。
- 全員参加の案では、対象者全員の明示的な参加可能回答を確定条件とする案を推奨。未回答・未定・条件未充足は参加可能に数えない。
- 表現できない条件は原文を計画側へ転送せず、追加質問やWeb入力、解決不能の表示へ進む。

## 実装への移行

2026-09-21、ユーザーから本方針でのブランチ作成・実装を依頼された。`feat/structured-scheduling` で既存の次の1回の調整へ適用する。具体的な追加型・デモ・承認条件は [実装契約](../../decisions/structured-scheduling-implementation.md) を参照。上の提案のうち全員の明示回答、構造化した時間条件、Discordでの案への回答を実装対象とする。全期間の複数回生成と運営方針の先行承認は別拡張。

## 調査時点の根拠と限界

事実：既存の `internal/agent/interpreter.go` と `internal/coord/interpret.go` に、項目抽出・本人確認前の下書き・原文を計画側へ渡さない設計がある。日程用の項目や全員参加の確定条件への拡張は未実施。

外部情報（確認日：2026-09-21）：OWASPは、プロンプトインジェクション対策として出力形式の検証、最小権限、人の承認などを組み合わせることを推奨する。
参照：https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html

設計上の判断：構造化だけでは、形式上正しい誤った値の抽出を防げない。プロンプトの禁止指示だけに依存する案、自由文の要約を後段へ渡す案は採用を推奨しない。原文をアプリDB・ログへ保存しないことと、Discordやモデル提供元での保持は別問題である。
