# 認証とDiscord連携の方式

決定日：2026-09-20。

## 決めたこと

ログインは Discord OAuth（`identify`）＋サーバーセッションCookieのみとする。追加の本人確認・アカウント連携の仕組みは今回入れない。

Discord ユーザーとアプリ利用者の紐づけは、既存の招待モデルで行う。

1. 管理者が招待時に相手の Discord ID（17〜20桁）を登録する。
2. この登録は「招待先」であり、その人として操作する権限にはならない。
3. 本人が Discord OAuth でログインした時点で所属を有効にする（`store.Tx.ActivateMemberships`）。

## 却下した選択肢

### Web登録 → 連携サーバーへの招待リンク → BotとDM → Web表示のコードを入力（二段階認証的な連携）

- ログインの身元が Discord と別（Google・メール等）の場合にだけ必要な手順。Discord OAuth でログインする限り、Discord ユーザーIDは認可の結果として検証済みで返るため、同じことを二度証明する作業になる。
- 現在の Bot は通知チャンネルへの HTTP POST のみ（`internal/notify`）で受信系を持たない。DM でコードを受け取るには Gateway 常時接続とイベント処理の新規実装が必要で、提出期限（9/22 15:00）までの残時間に見合わない。
- コード入力は総当たりとコードの口外という経路を新たに作る。OAuth より安全にはならない。

### Google アカウントでのログイン

- `users` は `discord_user_id` 前提で、招待→有効化の設計もそこに依存する。識別子が2系統になると重複アカウントとメール一致によるリンクの乗っ取りを新たに設計する必要が出る。
- 通知先が Discord なので、どのみち Discord アカウントは必要。「Discord を持たない人も使える」という便益が立たない。
- 将来入れる場合も、Google ログイン後に Discord OAuth を通すアカウントリンクで足り、コードのDMは不要。

### OAuth に `guilds.join` を追加して連携サーバーへ自動参加させる

- 同意画面が重くなる割に、調整負担の削減というデモの主張に寄与しない。招待リンクをWeb画面に置く手動参加で足りる。

## 残る前提

- 通知先チャンネルにメンバーが居ることは紐づけとは別の問題。グループ画面に招待リンクを置いて手動参加してもらう。
- Bot が DM を送るには共通サーバー所属と相手のDM設定が前提になるため、仕様どおり DM は必須にしない。
- 初期登録画面に、Discord の開発者モードを有効にして自分のIDをコピーする手順の案内を出す。
