# Discord・空き時間・ホーム表示の現行フロー統一

決定日：2026-09-22。並列開発の基点として、DiscordをWeb UIの代替入口にすること、普段の空き時間と開催回固有の例外を分けること、ホームで未完了の進行を状態別に一覧することを決める。関連：[Discordの常駐Bot](discord-interactive-agent.md)、[グループ種別とブック計画](group-kind-and-book-planning.md)、[並列開発runbook](../workflows/parallel-worktree-development.md)。

## 対象・デモ・外部連携・承認・成功指標

- 対象：WebまたはDiscord DMで輪読の日程・担当へ回答する参加者と、複数の開催回を確認するグループ参加者。
- 単一デモ：通知からDiscordで参加可否と日程条件を順番に回答し、Webと同じ構造化データを本人確認後に保存する。ブック担当は一度だけ承認し、ホームでは未完了の全枠を状態別に確認できる。
- 外部連携：既存のDiscord Bot・通知キューとOrcaRouter解釈器だけを使う。Discordの自由文は日程条件の抽出だけに渡し、同意・担当承認・保存をLLMに行わせない。
- 承認地点：自由文の下書きと週間空き時間は本人が確認して保存する。同意・担当の引き受け・担当確認は本人のDiscordボタンまたはWeb操作だけで記録する。
- 成功指標：通知後に「回答」と送り直さず操作できる、選択式の回答ではLLMを呼ばない、WebとDiscordが同じ最終状態になる、普段の空き時間が「未定」回答で無効にならない、担当承認を二重に求めない、ホームから未完了の全枠を状態別に確認できる。

## Discordの質問順と再開

- 個人向け通知から対象を束縛して直接開始し、別途「参加条件」「回答」と入力させない。複数対象を利用者が自発的に開始した場合だけ、対象選択ボタンを出す。
- 参加条件はWeb UIを正とし、対象選択 → 参加可否（ボタン）→ 日程条件と今回だけの例外（この段階だけ自由文をLLMで抽出）→ 構造化結果の確認 → 保存、の順にする。担当辞退は参加条件フォームに混ぜない。
- 案への同意、旧方式セッションの担当引受、ブック計画の担当承認・交代候補、開催3日前の担当確認、週間空き時間の登録・再確認も、通知または会話内のボタンから該当する通常のCoordinator操作へ接続する。管理者による作成・編集・削除はWebに残す。
- 「分からない」「最初から」「やり直し」は未保存の下書きを破棄し、同じ対象の最初の質問から即再開する。「中断」「あとで」「キャンセル」は未保存の下書きを破棄して会話を終了し、次回は保存済み情報から開始する。
- ボタン押下時はDiscord操作者、対象、所属、期限、現在の状態をサーバー側で再検証する。通知文や `custom_id` の値を認可根拠にせず、古いボタン・再送・連打で二重回答しない。再起動後に安全に失効させるか再検証して処理できる設計にする。

## 普段の空き時間と開催回固有の例外

- 普段の空き時間はユーザー単位の既存 `timezone`・`windows` を正とする。セッション画面は登録済みの内容を一覧し、`/weekly.html` の編集へ移動できるようにする。
- 開催回では「今回だけ参加できない日」（終日）と「今回だけ参加できる日時」を追加できる。ここでいう例外は毎週の曜日ではなく、対象期間内の具体的な日付である。特定日の時間帯はその日の週間設定を置換する。
- 開催回で毎週の曜日・時間帯を明示的に入力した場合は、本人の普段の空き時間をその内容で全置換する。マージはしない。画面と確認表示で「普段の空き時間も更新される」と明示する。開催回の曜日入力は日本時間なので、この経路では `Asia/Tokyo` として保存する。
- 開催回の保存入力には省略可能な `update_weekly_availability`（既定 `false`）を追加する。本人が週間予定を明示的に入力・変更したときだけ `true` にし、参加条件と同じトランザクションで普段の空き時間を全置換する。`true` なのに有効な週間時間帯がない入力は拒否する。参加条件タスクへの `submit` と本人による直接更新の両方で同じ意味にする。
- `schedule` が未指定または `unknown` でも、登録済みの普段の空き時間を候補計算に使う。今回だけの例外と普段の空き時間を合成する。未回答を参加可能扱いにはしない。
- 普段の空き時間の自由文解釈は下書きだけを返し、保存しない。公開契約は次とする。
  - `POST /api/me/weekly-availability/interpretations`
  - 入力：`{"text":"毎週水曜と金曜の19時から22時"}`
  - 成功：`{"availability":{"timezone":"Asia/Tokyo","windows":[{"weekday":3,"start":"19:00","end":"22:00"}]},"unclear":[],"needs_followup":false,"saved":false}`
  - `weekday` は既存週間契約と同じ `1=月曜〜7=日曜`。未知フィールド、不正な時刻、重複時間帯、他人の予定、保存・同意を求める指示を拒否または未確定として扱う。

## 担当承認とホーム一覧

- ブック由来の実セッションは、作成前にブック側で担当本人の承認が済んでいる。セッション案で同じ担当者へ `assignment` タスクを再発行せず、`reading_book_slots.assignment_status` を唯一の担当承認状態とする。担当が固定されていない旧方式のセッションだけ、従来の担当引受タスクを維持する。
- ホームの最上部は従来どおり「いま自分が回答する1件」を強調する。その下では、ブックの未完了枠を重複なく次の順で一覧する：自分の回答待ち、要確認、日程調整中、日時確定・実施待ち、調整開始待ち。完了済みは除外する。
- 一覧には実セッション作成前のブック枠も含める。MVPでは既存のグループ・ブック詳細APIを集約し、専用dashboard APIは追加しない。部分的な取得失敗を空状態に見せず、取得できなかったことを表示する。
- 参加条件の自由文プレースホルダーは、準備状況や説明時間を聞く旧文言をやめ、参加可否・普段の曜日時間・今回だけ出られない日の例に変える。

## 並列実装の境界

1. Discord担当：`internal/discord`、`internal/notify`、通知用store、`coord/dialog*` と通知接続。週間空き時間の保存規則やホーム画面は変更しない。
2. 空き時間担当：週間解釈API、普段の空き時間との合成・自動更新、`weekly.js`・`session.js`・参加条件フォーム。Discord会話状態とホーム一覧は変更しない。
3. 整合性・ホーム担当：ブック由来セッションの重複担当タスク解消と `index.js` の状態別一覧。Discord・週間解釈API・参加条件フォームは変更しない。

共通型や既存ファイルへの最小変更は許すが、境界外の仕様変更が必要なら独自に契約を変えず最終報告で止める。統合順は Discord → 空き時間 → 整合性・ホームとし、競合修正は統合ブランチで行う。

## 統合レビューで確定した補足

統合日：2026-09-22。

- ブック由来セッションの担当承認済み判定は、利用者が変更できるセッションJSONではなく、セッションに紐づく `reading_book_slots` が `accepted` で、担当者も一致する場合だけ信頼する。JSONだけを信頼する案は、手動作成時に担当引受を省略できるため却下した。
- 通知ボタンは作成時のブック計画版・対象枠・参加条件タスクへ束縛し、現在状態を再検証する。最新の未回答対象を押下時に探す案は、古い通知が新しい計画へ作用するため却下した。
- Discordで毎週の曜日・時間帯を明示した場合は、確認画面に全置換を表示し、保存時だけ参加条件と同じトランザクションで普段の空き時間を更新する。解釈直後の保存は、本人確認を飛ばすため却下した。
- ホーム集約は同時通信数を全体で4件に制限し、一覧・詳細・メンバー情報の一部取得失敗を明示する。失敗を空一覧として扱う案と、完了済みブック枠を理由に通常のセッションまで隠す案は却下した。
