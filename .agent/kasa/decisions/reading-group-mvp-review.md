# 輪読MVPのレビュー反映

日付：2026-09-19。ユーザーがレビュー内容の修正を依頼したことを受けた仕様変更。実装と効果測定は未完了。

## 新しく確認できた前提

ユーザーの輪読には固定の幹事がおらず、輪読用LINEでメンバー同士が日程調整・担当分けを行っていた。以前の「幹事の作業削減」「実運用でDiscordを使っている」という前提は、この利用事例の説明として採用しない。

## 決定と理由

| 項目 | 以前の方針 | 今回の方針・理由 |
| --- | --- | --- |
| 中心の機能 | 立ち上げ→予定変更→当日進行を順番に実装 | 既存会の予定変更→再計画→同意→反映→通知を先に完成。30〜40時間で評価の核を守る |
| 入力 | 本・メンバー・頻度が中心 | 節・テーマ、進捗、準備済み範囲、説明可能時間も登録。計画の根拠を明確にする |
| 同意 | 初回の管理者承認と本人同意の関係が曖昧 | 初回から本人の引き受けが必要。多数決の分母と案の版を固定 |
| 設定と拡張 | 委任設定画面、共通コア＋用途別プレイブック | MVPのルールを固定し、コードの責務分離にとどめる。汎用拡張基盤は作らない |
| 負担の検証 | 幹事へのヒアリング・主催者の操作数 | LINEの調整メッセージと参加者全体のWeb送信等を比較。媒体の置換を効果と誤認しない |
| 比較期間 | 未定 | 同期間の実運用を基本とし、開催回数と案件の種類・数を併記。短期提出では過去事例の再現試験と明示 |
| 通知 | OAuthで通知先も自動取得する想定 | OAuthの本人確認とBot設定を分離。指定チャンネル1つで検証 |
| 分担 | 友人がログイン・通知全般 | 友人が画面・Discord設定、kasaがGo内の認証・通知処理。実行時のサーバーを増やさず、境界を2人で確認する |
| 評価 | 開発後半にケース数とデモを決める | 固定ケース・期待結果・4分台本を仕様化。計測値は未測定のまま区別する |

## 見送るものと残る懸念

日程の自動調整、当日の自動司会、LINE連携、教材全文取り込み、会議プレイブックは対象外。従来の①→②→③で運営全体を一周する構想は将来案として残す。

参加者がWeb＋Discordを受け入れるか、調整操作が実際に減るかは未検証。件数だけでは時間や心理的負担を測りきれず、再現試験は実運用の効果を証明しない。ヒアリングと試用結果を併記する。

モデル、費用上限、データ保持条件、APIの具体的な形、LINEの集計対象は実際の確認を経て決める。元の企画メモは検討時点の記録として保存する。

現行の仕様は [spec.md](../../decisions/spec.md)、評価方法は [evaluation.md](../../decisions/evaluation.md) を参照。

## 追記：用途分離と雛形の扱い

同日の追加指示により、用途別処理は共通インターフェースを持つアプリ内部のPlaybookとして分離する。起動時の静的登録とし、会議機能や動的ロードの仕組みは作らない。上記の「汎用拡張基盤は作らない」は、用途を分離しないという意味ではない。

フロントは既存動作を保ち、共通部品・輪読用画面のファイル配置だけを追加する。先行して追加したバックエンドの雛形・登録処理は専用ブランチに分け、追加の業務実装は開始指示まで行わない。評価資料を `.agent/decisions/` に移し、当面 `docs/` は更新しない。

## 追記：フロントとバックエンドのAPI契約

公開APIを [api.md](../../decisions/api.md) のmvp-1として決定。画面は同一オリジンのJSON APIとセッションCookieを利用し、更新は非同期受付、状態確認はポーリングとする。WebSocketや自由文の解釈APIはMVPに含めず、構造化回答で独立した画面開発と評価を可能にする。

グループ作成者が既知のDiscordユーザーIDを招待先として登録し、OAuthで本人と紐付ける。参加者による準備回答・担当引き受け・投票を分離し、旧版への同意や再送による重複をAPI契約で定義する。DB・内部型は公開契約へ変換し、用途固有の型を共通処理へ混ぜない。実装・モック作成はこの決定とは別作業。
