# スキーマ変更：版ごとの SQL を積み上げ、起動時に未適用の版だけ流す

決定日：2026-09-20。関連：[認証とDiscord連携の方式](auth-and-discord-linking.md)。

## 背景

テーブル定義は `internal/store/schema.sql` 1枚で、起動のたびに丸ごと `Exec` していた。中身がすべて `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` なので、次の性質があった。

- 新しいテーブル・索引を足すのは、ファイルに書き足すだけでよい。
- **既存テーブルの列追加・制約変更は、既存の DB に反映されない。** `IF NOT EXISTS` が素通りするため、手元の `data/app.db` を消さない限り古い形のまま動き続ける。

開発中は `make db-reset` で消せば済んでいたが、次の2つが近づいて限界になった。

- デモ用の初期データを作り込む段階に入り、DB を消す＝作業のやり直しになる。
- 共同作業でブランチを行き来すると、各自の手元の DB がどの形なのか分からない。「自分の環境だけ動かない」の原因が特定できない。

## 決めたこと

版番号付きの SQL を積み上げる方式にする。

1. `internal/store/migrations/<4桁の版番号>_<説明>.sql` に置き、`embed` で実行ファイルに同梱する。
2. 起動時（`store.Open`）に、適用済みの版番号より大きいものだけを昇順で適用する。
3. 適用済みの版番号は `meta` テーブルの `schema_version` に入れる。`meta` は元から定義だけあって使われていなかったので、そこに載せる。
4. **1つの版＝1トランザクション。** 同じトランザクションで版番号も更新する。途中で失敗すればその版の変更は丸ごと巻き戻り、版番号も上がらない。直して起動し直せば同じ版からやり直せる。
5. DB の版がプログラムの知る最大の版より新しければ、開かずにエラーにする。古いプログラムが新しい DB を壊さないようにするため。

### 既存の DB の引き継ぎ

版番号の記録がない DB（この変更より前に作ったもの）は版 0 として扱い、0001 から適用する。0001 は従来の `schema.sql` をそのまま移したもので中身は全部 `IF NOT EXISTS` なので、**既存の DB に対しては何も起こさずに版番号だけが 1 になる**。作り直しも手作業も要らない。

この性質は 0001 に限った前提なので、ファイル先頭にその旨を書いて固定した。0002 以降は冪等でなくてよい（版番号で二重適用を防ぐ）。

### SQLite の作り直し手順への対応

SQLite には列の削除・型変更・制約変更がない。新しい表を作って移し替え、元を落として改名する手順になるが、この間は外部キー検査を止める必要がある（公式の 12 ステップ手順）。

ファイルの**先頭行**に `-- foreign_keys: off` と書いた版は、適用中だけ `PRAGMA foreign_keys = OFF` にする。切り替えはトランザクションの中では効かないので `BEGIN` の前に行う。接続を1本に固定してあるので、設定が別の接続へ逃げる心配はない。コミットの直前に `PRAGMA foreign_key_check` を実行し、参照を失った行があればコミットせずに巻き戻す。

## 却下した選択肢

### `schema.sql`（現在の完全な定義）と `migrations/`（差分）を両方持つ

スキーマを1枚で読めるのは利点だが、変更のたびに2か所を直す必要があり、片方を忘れるとズレる。しかもズレは「新規 DB と既存 DB で形が違う」という最も気づきにくい形で出る。現在の定義は「全部の版を適用した結果」に一本化した。

代わりに、スキーマを1枚で読みたい場合は `docs/database.md`（列の意味とサンプル付き）を見るか、`sqlite3 data/app.db .schema` を使う。

### golang-migrate などのライブラリを入れる

必要なのは「番号順に流す」「どこまで流したか覚える」の2つだけで、実装は 200 行に満たない。CLI の導入手順が増え、ハッカソンの環境構築の説明が長くなるほうが損。既存の依存も `modernc.org/sqlite` と `golang.org/x/text` の2つに絞ってある。

### ロールバック用の SQL（down マイグレーション）も書く

down は書く機会が少ないわりに、書いた時点では正しさを確かめられず、いざ使うときには腐っていることが多い。この規模では「失敗した版を直して入れ直す」「手元なら `make db-reset`」で足りる。**本番運用に入るなら再検討する。**

### 版番号ではなく、適用済みファイル名の一覧を記録する

ファイル名を後から変えられる利点があるが、`meta` の1行に収まらず専用テーブルが要る。版番号1つのほうが「今どの形か」を一言で言えて、取り違えの検出（新しすぎる DB）も比較で書ける。

## 実装の範囲

- `internal/store/migrate.go`（読み込み・版番号の管理・適用）
- `internal/store/migrations/0001_init.sql`（旧 `schema.sql` をそのまま移動）
- `internal/store/store.go`：`Open` が `schema` の直接実行ではなく `migrate` を呼ぶ。**公開している型・関数の形は変えていない**ので、呼び出し側（`cmd/server`・各テスト）に変更はない。
- `Store.SchemaVersion`（確認・調査用）

- `docs/database.md`：参照先を `migrations/` に更新し、「スキーマの変更」節と `meta` の `schema_version` を追記（ユーザーの指示により更新）。
- `README.md`：「データベース」節を追加。

## 残る確認事項

- 本番相当の運用（データを消せない環境）に進むなら、down マイグレーションと、適用前バックアップの手順を決める。
