# グループ種別と、複数ブックの全体計画・自動進行

決定日：2026-09-21。ブランチ：`feat/group-book-planning`。関連：[ブックとセッションのモデル](book-session-model.md)、[日程調整の入力境界](scheduling-input-boundary.md)、[開催日時をエージェントが決める](schedule-by-agent.md)、[構造化した日程調整の実装契約](../../decisions/structured-scheduling-implementation.md)。

## 対象・デモ・評価

- 対象：固定の幹事がいない輪読グループの参加者。
- 単一デモ：`reading` グループを作る → 同じグループへ複数ブックを登録 → 全枠（開催目安・章割り）と、AIの全体計画・担当の仮割り当て → 各担当者が自分の担当分を承認 → 各回の調整開始日になったらその回だけ日程調整を開始（例外の参加不可日を集め、AIが候補を提案）→ 日時確定 → 開催3日前に担当者へ最終確認 → 交代が必要なら候補を提案し、新担当者本人の承認後に変更。
- 外部連携：既存のOrcaRouter境界と、既存のDiscord通知キューだけ。LLMに同意・承認を作らせない。個人的な理由は保存・共有しない。
- 成功指標：複数ブックの同時進行／登録だけで最初の調整が始まらない／時計を進めると対象枠だけが一度だけ始まる／担当者の同意と直前確認を追跡できる／再起動・再処理でセッション・タスク・通知が重複しない。
- 実装済みかどうかは、下の「検証と限界」を参照。実モデル・実Discord・実参加者での検証は未実施。

## 決定

### グループ種別（`playbook_id`）

- グループは単一の `playbook_id` を持つ。対応する値は `reading` だけ。作成後は変更できない（`PATCH` は `name` だけを受け、`playbook_id` を含めると未知項目として拒否する）。
- 既存DBのグループは、列追加（`groups.playbook_id` の既定値 `reading`）で輪読として読める。作成時に省略した従来の呼び出しも `reading` になる。未対応の値は `validation_failed`（`playbook_id`）。
- グループ名の変更は管理者だけ（サーバー側で所属と権限を確認）。名前の変更は繰り返しても同じ結果になるため、再送キーは要求しない。

### 複数ブックと「登録」「開始」の分離

- 同じグループへ複数ブックを登録でき、同時に進められる。登録は1冊ごとに独立した再送可能な処理で、複数冊を1つの大きなトランザクションにしない。
- 登録時に、期間・回数・章から**全枠**を作る（開催目安の期間を等分、全章を登録順に連続した範囲へ）。実セッション・参加条件のタスク・開催回の通知は作らない。旧契約の `session_creation_mode`（`sequential`/`all`）と `initial_session` は入力から外した（DB列は互換のため残し、新規は常に `all`）。
- 各枠の実セッションは、`開催目安の開始日 − adjustment_lead_days`（1〜30日、推奨7日、JSTの0時）を迎えたときに、その枠だけ作る。初回の調整開始日がすでに過ぎている枠は、計画の成立後の最初の処理で始まる。
- 自動進行は「期限イベント」ではなく、DBの状態から毎回導く（下の却下案を参照）。開始は「枠が未開始のときだけ `active` にする」条件付き更新と、同じトランザクション内のセッション作成でまとめるため、二重に始まらない。

### 全体担当計画と承認

- 登録後、AIが全体の章割り・開催目安・担当者を**提案**する（`plan_status`：`planning` → `awaiting_approval` → `approved`。失敗時は `needs_attention`）。旧ブックは `legacy` で自動進行の対象外。
- AIは提案しか作れない。プログラムが次を検証し、満たさなければ確定せず（AIには修正を返し、直らなければ管理者判断待ち）、保存直前にも最新の状態で再検証する。
  - 章：全章が登録順に、欠落・重複なく、各回1章以上。存在しない章を作れない。
  - 開催目安：全体期間内で、回の順に重ならない。
  - 担当：在籍していてログイン済みのメンバーだけ（存在しないIDは拒否）。同じ人を続けて担当にしない。同じグループで同時進行中の**全ブック**の未完了の担当を合わせた最大負担が、規則だけで作った計画（基準）を超えない。
- 新しいブックを追加しても、既存ブックの割り当ては変更しない（新ブックの計画が既存の負担を読むだけ）。
- 承認：割り当てられた各メンバーが、自分の担当分を本人が承認する。管理者の同意件数は要求しない。未回答を承認扱いにしない。1件でも未承認・変更希望があれば計画は成立しない。
- 担当変更：担当者が変更を希望すると、AIが負担履歴から候補を**提案**する。候補は、現在の担当者・この枠で断った人・在籍していない人・負担が最小でない人を除き、隣の回の担当は他にいれば避ける（検証層で強制）。候補**本人**が承認して初めて入れ替わる。AIが無承認で交代させる経路はない。担当変更だけなら他の担当者の承認は取り直さない。承認済みの担当者が脱退した場合は、変更希望として扱う。
- ブックの編集は、最初の実セッションが始まる前だけ許可する（始まった後は 409 `invalid_state`）。章・期間・回数・1回の長さ・リード日数を変えたときは、以前の担当承認を無効にして全枠と計画を作り直す。書名・ISBN・目次情報だけの変更では承認を保つ。管理者は計画の再生成も依頼できる（AI失敗時の再開など）。
- 実セッションの開催回データには、承認済みの担当者を固定する。発表の担当はその人に限られ（検証で強制）、担当者が欠席・辞退なら他の人へ回さず管理者へ戻す。担当が変わった実セッションは、担当だけの変更として再調整する。

### 普段の空き時間（週間空き時間）

- ユーザー共通で1件保存する（`GET/PUT /api/me/weekly-availability`）。タイムゾーン（IANA名）と、曜日（1=月〜7=日）・開始・終了（終了のみ 24:00 可）の配列。区間の重複・開始≧終了・不正な曜日・時刻を拒否する。更新日時はサーバーが決め、入力させない。未登録は `windows=[]`・`updated_at=null`（時刻を作らない）。
- 各回では、既存の参加条件収集で「今回だけ参加不可」を集める。時間帯を答えていない参加者は、本人が登録した普段の空き時間を使う（タイムゾーンは実際の日時に直してから重ねる）。**この回で時間帯を答えた人は、本人の回答を優先**する。参加条件（出欠）に未回答の人は、普段の空き時間があっても候補に数えない。今回だけ参加不可の日は普段の空き時間に優先する。
- ブック登録後、管理者はメンバーへ登録または再確認を依頼できる（未登録＝登録依頼、30日超＝再確認、最近登録した人は対象外。同じ日の同じ相手へは1回だけ）。
- 日程候補は、同じ人が別のブック・別のグループで確定済みの予定と重ならないことを、AIの出力に対しても検証する（衝突する日時しかなければ確定せず管理者へ戻す）。

### 開催直前の担当者確認

- 日時が確定した枠で、開催3日前に担当者確認を**一度だけ**作る。2日前に未回答なら**一度だけ**催促する。1日前でも未回答なら「管理者判断待ち」として管理者へ知らせる。自動で別の担当者に確定しない。管理者判断待ちの間も、担当者本人は確認できる。
- 段階の間は最低1時間空け、遅れて確定した回でも確認・催促・エスカレーションを一度に連続して送らない。
- 確認は「確認」または「変更希望」。現在の担当者本人だけが回答できる。変更希望は上の担当変更の流れに入る。担当変更が3日前の窓の中で本人承認されたときは、新担当者の確認は済みとして記録し、旧担当者の確認は無効にする。

### 通知・費用・追跡

- ブックの個人宛て通知（承認依頼・担当変更・直前確認・催促・エスカレーション・空き時間の依頼・管理者判断待ち）は、既存の `group_notifications`（受信者ごとの個人DM、重複キー付き）へ載せ、共通チャンネルへは退避しない。この表の種別制約は外した（旧DBは行を保ったまま表を作り直す移行を入れた）。
- ブックの計画の費用は、案件に属さないため `llm_calls.lookup_id` にブックのIDを入れて追跡する。1回の計画あたり最大8回、一時的な障害の再試行は最大3回。
- 計画の作成・承認・変更・直前確認は `reading_book_log` に、私的な理由を含めず追記する。確認は (枠, 担当者) ごとに1行（`reading_slot_confirmations`）で、催促・エスカレーションの時刻を持つ。

## 採用理由

- 既存の日程提案・同意処理（開催回・案件・タスク）は変えずに、その手前にブック単位の計画を置くと、1回分の調整を必要になった時点で始められ、未開始の回が参加者へ依頼や通知を出さない。
- 「AIは次の一手を選ぶだけ、やってよいかはプログラムが判定する」（仕様書第4節）を、章・メンバー・負担・日程の検証層で保つ。LLMには同意を作るツールを渡さない。
- 自動進行を状態から導けば、再起動・再処理・時計の巻き上げに対して自然に冪等になり、イベントの取りこぼしも起きない。

## 却下した選択肢

- **全回の調整を一斉開始／登録時に最初の回を即開始**（前回から継続して却下）：先の予定は変わりやすく、不要な確認と通知を出す。今回の要件（登録だけで最初の調整を始めない）にも合わない。
- **章を人が回ごとに指定する**（前回の決定）：今回は、全章を登録順に連続して割り当てる決定的な分割にAIの提案（境界・担当）を載せ、プログラムで欠落・重複を検証する形へ変えた。章の重さを推測しない（章の数だけで分ける）点は維持する。
- **ブックの自動進行を既存の `events` 表へ登録する**：`events` は開催回を必須にしており、未開始の枠にはまだ開催回がない。状態から毎回導けば追加のイベントが不要で、取りこぼしもない。
- **ブック用の新しい通知表を作る**：送信・失敗・成否不明の扱いを二重に持つことになる。既存の個人DM表の種別制約だけを外して再利用した。
- **管理者の承認を必須にする／管理者の同意件数を要求する**：担当本人の承認が唯一の同意で、管理者が代行しない方針（仕様書第4節）に反し、固定の幹事がいない会の前提にも合わない。
- **担当変更のたびに全員の再承認を求める**：担当だけの変更では他の人の担当分は変わらない。
- **AIが担当者を自動で交代させる／候補を管理者が代理で承認する**：無承認の確定になる。
- **LLMが失敗したときに規則だけの計画へ静かに切り替えて確定する**：品質の違いが見えなくなる。LLMモードでは失敗時に管理者判断待ちにし、規則だけの計画は `AGENT_MODE=fake` と検証の基準にだけ使う。
- **未回答のメンバーへ普段の空き時間から回答を作る**：本人の回答を推測しない。出欠に答えた人が時間帯を答えていない場合に限り、本人が登録した普段の空き時間を使う。
- **週間空き時間をグループ・ブックごとに持つ**：同じ人が複数の会に出るため、ユーザー単位で1件にした。
- **`initial_session` / `session_creation_mode` を黙って無視して受け付ける**：未知フィールドの拒否を維持する方針に反するため、旧項目は拒否する。

## 検証と限界

- 実施：Goの全パッケージテスト（`-race` の coord・store・e2e を含む）、`go vet`、ビルド、HTTP経由のE2E（登録→計画→承認→時計を進めて開始→日時確定→3日前確認→担当交代、再起動を挟む）。旧DBの列追加・通知制約の緩和・グループ種別の既定値。
- 未実施：実モデル（OrcaRouter）での計画の品質・費用、実Discordへの送信、実参加者の操作負担。
- 限界（未対応）：
  - 調整開始日を過ぎて開催目安の期間も終わった枠は、自動では開始せず、管理者へ知らせる（`attention_reason`）。開始後のブックは編集できないため、回復手段は未提供。
  - 担当変更の候補を作れず管理者判断待ちになった枠には、管理者が再開する操作がない（計画の再生成は最初のセッション前だけ）。
  - 週間空き時間を登録済みの人でも、既存のDM対話・画面は時間帯を再度聞く。バックエンドは登録済みの空き時間を使って候補を作る。
  - グループを削除しても、送信待ちのブックDMは取り消さない。
  - 既存の画面（`src/frontend/`）は旧契約（`initial_session`・`session_creation_mode`）のままで、新契約に合わせた更新が必要。
