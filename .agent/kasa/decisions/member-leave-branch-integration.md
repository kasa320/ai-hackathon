# メンバー脱退・グループ削除ブランチの統合

更新日: 2026-09-21

## 事実

- `origin/kodera` は、`groups.deleted_at`、`members.left_at`、グループ通知テーブルと Store 層の操作を追加している。
- `feat/member-leave` は同じDB変更に加え、API、調整処理、個人DM通知、Web UI、E2Eテストまで一つの操作フローとして実装している。
- `feat/member-leave` の基点は現在の `master` より古く、ブランチ全体をそのままマージすると、後から追加された認証、目次取得、輪読画面の変更と競合する。
- 現段階では保存すべき本番データはなく、DB変更は新規DBの作成で適用する。既存DBを保持するマイグレーション基盤は未導入である。

## 決定

- `feat/member-leave` の機能コミットを採用し、現在の `master` を基点にした `integrate/member-leave` へ載せ直す。
- 対象ユーザーは、グループを離れる一般メンバーと、グループを論理削除する管理者とする。
- MVPの単一デモフローは、本人による脱退または管理者による削除、関連処理の停止、状態保存、残留メンバーへの個人DM通知、画面からの非表示までとする。
- 外部連携は既存のDiscord個人DMに限定する。個人DMの失敗時に共通チャンネルへ送らない。
- 脱退は本人操作、削除は管理者操作と確認ダイアログを承認地点とする。開催中の回がある場合はサーバー側でも拒否する。
- 成功条件は、権限と開催中制約が守られ、過去データを保持したまま今後の処理から対象を除外し、受信者別通知を保存できることとする。
- 公開契約の `docs/` は凍結中のため、この統合では更新しない。

## 却下した選択肢

- `origin/kodera` のみを採用する案は、Store 層だけではユーザーが完了できる操作フローにならないため却下した。
- `feat/member-leave` をそのままマージする案は、現在の `master` より後に追加された実装を競合や巻き戻しの対象にするため却下した。
- この統合と同時にマイグレーション基盤を導入する案は、現段階の新規DB前提を越えて変更範囲が広がるため見送った。実データ投入前に改めて決定する。

## 検証

- `go test ./... -count=1`
- `go vet ./...`
- `gofmt -d internal/api internal/apitypes internal/coord internal/notify internal/store tests/e2e`

いずれも `integrate/member-leave` で成功または差分なしを確認した。
