# 現行ブック運営フローに合わせた開発モード

決定日：2026-09-22。ブランチ：`feat/update-dev-mode`。関連：[グループ種別と、複数ブックの全体計画・自動進行](group-kind-and-book-planning.md)。

## 対象・デモ・評価

- 対象：ブック登録後の時間依存処理を、外部サービスや実時間を待たずに確認する開発者・デモ実施者。
- 単一デモ：2冊の全体計画を確認して担当を承認し、時計を進めて各回の日程調整を開始し、確定後に開催3日前の担当確認を行う。
- 外部連携：`DEV_MODE=1` と `AGENT_MODE=fake` のローカル環境だけで成立させる。Discord・OrcaRouterは必須にしない。
- 承認地点：全体計画の担当承認と開催直前の担当確認は、通常の業務APIとタスクを通す。シードがDBへ承認済み状態を直接書かない。
- 成功指標：各シナリオが意図した状態に到達し、時計進行の応答時点で期限到来処理が完了し、画面の再読込と競合しないこと。

## 決定

- 現行フロー用に `book_plan_demo`、`book_schedule_demo`、`assignee_confirmation_demo` を用意する。前2つは同じグループに2冊を同時投入し、複数ブックを確認できる状態にする。
- シードは通常の Coordinator 操作でグループ・ブック・空き時間・承認・開催回を作る。日時案は規則ベースの Planner を使い、外部LLMを呼ばない。
- 時計進行APIは時刻を進めた直後に期限到来処理を同期実行し、完了後の時刻・オフセット・処理件数を返す。バックグラウンド処理への通知も従来どおり残す。
- デモバーには現在時刻、1時間・1日・7日の進行、処理中表示、処理件数、失敗理由を表示する。
- 既存E2Eと過去デモの再現用に `initial_demo` と `replan_demo` は互換シナリオとして残す。

## 却下した選択肢

- シード専用SQLで最終状態だけを作る：通常処理の制約や承認経路を迂回し、不整合を隠すため。
- 時計進行後に一定時間待って画面を再読込する：処理時間に依存して不安定になり、完了条件を検証できないため。
- 旧シナリオを削除する：既存のE2Eと、開催回単位の再計画デモを不必要に壊すため。
