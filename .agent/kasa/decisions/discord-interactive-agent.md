# Discord の常駐Botと対話での参加条件の更新

決定日：2026-09-20。実装ブランチ：`feat/backend-interactive-agent`。
関連：[認証とDiscord連携の方式](auth-and-discord-linking.md)、[自由文の解釈](free-text-interpretation.md)。

本書は、関連文書の「Discordでの対話は見送る」という判断を更新する。原文をアプリDB・実行ログに残さず、本人確認後に構造化した参加条件だけを保存する境界は維持する。

## 決めたこと

Discord に常駐Botを置き、**DMでの対話から参加条件を更新できる**ようにする。安全性は次の3つで確保する。

1. **対話エージェントにできるのは、規定された変数の値を決めることだけ。** 文章も、保存も、他人の値も触れない。
2. **会話の記憶は検証済みの変数だけ。** 発言の履歴をLLMに渡さない。
3. **参加条件の保存は本人のボタン押下でのみ。** 会話の原文・未保存の下書きは永続化しない。呼び出し費用と保存済みの差分は記録する。

Webからの入力・修正はこれまで通り使える。DMはWebの代わりではなく、同じ変数へのもう一つの入口。

## エージェント間で共有する変数

### A. 対話エージェントが値を決めてよい変数

ツールの引数のすべて。LLM が世界に対してできるのはこれだけ。

| 変数 | 型 | 再検証（プログラム） |
| --- | --- | --- |
| `attendance` | `attending` \| `absent` | 列挙値のみ |
| `willing_to_present` | bool | — |
| `prepared_section_ids` | 節IDの配列 | 登録済みの節IDのみ |
| `explainable_section_ids` | 節IDの配列 | 登録済みの節IDのみ。`prepared` との関係は両項目の確定後に検証 |
| `max_presentation_minutes` | int | 0〜持ち時間 |
| `unclear` | 上の項目名の配列 | 上の5つの名前のみ |
| `needs_followup` | bool | `unclear` が空でないことと一致。進行はプログラムが再計算 |
| `out_of_scope` | `null` \| `schedule_change` \| `partial_attendance` \| `other_member` | 列挙値のみ。**何も解除しない** |

上5つのうち `attendance` 以外は `data` の中身で、既存の `reading.PreparationSchema()` と同一。
`unclear` / `needs_followup` / `out_of_scope` は**トップレベル**（`data` の外）に置く。
`data` の中へ足すと、保存時の `decodeStrict`（`DisallowUnknownFields`）に拒否される。

### B. プログラムだけが決める変数（LLM に書かせない）

LLM に見せるのは `pending_question` だけ。それ以外の識別子・版・操作は渡さない。

| 変数 | 出どころ |
| --- | --- |
| `member_id` | Discordの発言者／ボタン操作者 → `users.discord_user_id` → 対象の開催回のグループの `members` |
| `session_id` | 対象選択で決定。ボタンからはサーバー上の選択状態・下書きを参照する |
| `expected_revision` | 会話開始時に読んだ `session.revision` |
| `proposal_id` / `proposal_version` / `task_id` | タスクの値 |
| `decision` | ボタンの `custom_id` |
| `pending_question` | いま聞いている項目名。プログラムが `unclear` から選ぶ |
| `draft_id` | 推測困難な下書き識別子。値または確定状態が変わるたびに振り直す |

「Cさんの分も登録して」と書かれても他人の行を更新できない。ただし他人の情報を本人の値として誤抽出する可能性は残るため、保存前に全項目を本人へ表示する。
OAuthでのユーザー登録・所属有効化が済んでいない利用者にはWebログインを案内する。DM受信を理由にユーザーや所属を自動作成・有効化しない。登録済みならWebのセッションCookieは要求せず、Discordイベントの操作者IDから認証する。

### C. 会話の進行にだけ使う変数（メモリのみ・保存しない）

利用者ごとに会話は1つとし、対象の開催回を束縛する。`slots`、`unclear`、`pending_question`、
`draft_id`、`expected_revision`、確認表示用の不変スナップショットとメッセージID、`expires_at`（最終操作から30分）をメモリに置く。
`misses`（空振り回数）・`cooldown_until` は利用者単位で持ち、開催回の切替ではリセットしない。

LLM が毎ターン見るのは **Aのスキーマ・現在の値と未確定項目・`pending_question`・今回の1発言・対象の節一覧と持ち時間**。
最後の文脈は既存の `InterpretContext` を使う。これがないと節名をIDへ対応づけられない。他人の参加条件は渡さない。
`pending_question` はプログラムが選んだ項目名なので、「はい」のような短い返答がどの項目への答えかを
履歴なしで決められる。発言の履歴は渡さない。

### 未確定値と更新の契約

- 保存済みの本人の値があれば初期値とし、未言及の項目はその値と確定状態を維持する。未登録なら全5項目を `unclear` に入れる。
- ツールは全項目を持つ候補を返す。未確定の項目には型を満たす仮値（`attending` / `false` / `[]` / `0`）を置けるが、`unclear` に含まれる値を確定値として表示・保存しない。既存の値を仮値で上書きするのは、その項目を未確定に戻す場合だけ。
- `unclear` は「今回言及しなかった項目」ではなく「候補全体でまだ未確定の項目」。`false`・`0`・空配列と未確定を区別する。今回は何も変更しない場合も、既存の完全な候補は確認画面に進める。
- JSON Schemaだけに依存せず、必須キーの存在・型・未知キー・列挙値・配列の重複をプログラムで検証する。現在の `checkInterpretation` の文字数検査だけでは `unclear` の名前制限を満たさない。
- `out_of_scope != null` ならそのターンの候補全体を捨て、値を変更しない。扱える変更も混在していれば、それだけを改めて送るよう案内する。

## 1ターンの流れ

```
DM 受信
 ├ Bot自身・Bot発言・サーバー内発言を除外。本文以外の添付・編集イベントは解釈しない
 ├ message.id で重複排除（Gateway は再送しうる）
 ├ 送信者 → user を解決 → 対象の開催回を決定 → そのグループの member と変更権限を確認
 ├ 定型の読み取り・取消・対象切替を処理（LLM不要）
 ├ 更新の発言なら、表示済みの確認ボタンをサーバー側で無効化
 ├ クールダウン中／LLM予算超過 → 定型文で Web へ誘導（LLMを呼ばない）
 ├ 現在値・未確定項目・質問中の項目・対象の文脈・今回の発言で解釈（呼び出し前に予算確保）
 ├ 返るのは record_preparation の引数だけ（文章は返させない）
 ├ 出力の形と項目を部分検証
 ├ out_of_scope が返った → 扱えない旨を定型文で答える（進捗なしに数える）
 ├ 有効な候補を適用。値・確定状態が変われば draft_id を振り直す
 ├ 未確定項目なし → 全体検証 → 確認メッセージ＋ボタン（変更なしの確認も含む）
 ├ 進捗なし（スロットが変わらず unclear も減らない）→ 空振り +1。3回でクールダウン10分
 └ 進捗あり → 残った unclear から次の質問を選ぶ（定型文）
```

**Bot の発話はすべてプログラムが作る定型文。**LLMの任意の出力文字列は転記しない。
節名・表示名など既存の可変文字列はエスケープし、意図しないメンションを `allowed_mentions` で抑止する。

読み取りは「予定」「いまの予定を教えて」などの明示した定型入力／ボタンで受け付け、LLMを使わず保存済みの計画を返す。
任意の自然文を決定的に分類できるとは仮定しない。クールダウン中も読み取り・取消・Webへの誘導は使える。
進捗があれば `misses` を0に戻す。モデル・通信障害は空振りに数えず、値を維持して再送またはWebを案内する。

## 検証は二段階

保存用の検証をそのまま毎ターン当てると、段階的な聞き取りが成立しない。
`ValidatePreparation` は担当できるなら説明できる節1件以上と1分以上を必須にするため、
「説明できます」とだけ答えた段階で拒否される。

| いつ | 何を見るか |
| --- | --- |
| 会話中（毎ターン） | 型・列挙値・登録済み節ID・`0 ≦ minutes ≦ 持ち時間`。**未確定を許す**。`explainable ⊆ prepared` は両項目が確定した時点で確認 |
| 確認表示前と保存時 | 既存の `ValidatePreparation` を全体に適用。通らなければ確認ボタンを出さず、保存もしない |

用途側に部分検証のメソッドを1つ足す（`PreparationInterpreter` に追加）。
項目間の矛盾はエラーに対応する項目を `unclear` に戻して定型質問を出す。たとえば説明できる節が準備済みの節に含まれない場合、勝手に「準備済み」を増やさず聞き直す。
欠席／担当不可が確定した場合の従属値は用途の規則で正規化できる（担当不可、説明可能な節は空、時間は0）。正規化した結果を必ず確認画面に含める。
Webの単発解釈はこれまでどおり保存可能な候補を返す。DMの部分検証をWebへ一律適用せず、現在値と質問を渡す対話モードで使い分ける。

## 確認ボタンは「表示した下書き」に束縛する

`expected_revision` は保存済みの版しか見ないので、**未保存の下書きの変化を検出できない**。
「15分」の確認を出したあと追加の発言で「30分」に変わり、古いボタンを押すと、
表示と違う値を承認した扱いになる。二段構えで防ぐ。

| 守る対象 | 手段 |
| --- | --- |
| 未保存の下書きが変わった | `custom_id` の `draft_id` と会話状態の現在の `draft_id` の一致を確認 |
| 保存済みの状態が変わった | `expected_revision`（既存の仕組み） |
| 会話状態が消えた（TTL・再起動） | 最初から確認し直す |

値・確定状態・対象・読み込んだ版の変更で `draft_id` を振り直す。訂正を受信した時点でも古い確認を無効にし、LLM処理中や解釈失敗時に古い値を保存できないようにする。確認を再発行するときも新しいIDを使い、古い確認を再有効化しない。

確認表示は開催回名・開催日時・全5項目を含み、正規化済みの値を不変スナップショットとして保持する。
`custom_id` は操作と `draft_id` の参照だけにし、値は埋め込まない。押下時に操作者・DMチャンネル・確認メッセージID・有効期限・現在の下書きとの一致を検証する。
保存するのはこのスナップショットであり、その時点の可変スロットではない。所属・開催時刻・版は保存トランザクション内でも再検証する。

保存には既存の `store.IdemKey` を使い、利用者と `draft_id` で同じキー、表示した値から同じ本文ハッシュを作る。
連打・イベント再送は1回の保存として処理し、成功後はボタンを無効化する。再起動後に下書きがなければ値を再構築して保存せず、保存済みの状態を読み直す。

### 並行処理とDiscordへの応答

MVPはBotを1プロセスで動かす。利用者ごとにDMとボタン操作の状態遷移を直列化し、重複IDの確認と登録も不可分にする。
入力処理中の追加DMは保持せず「処理中です。応答後に再送してください」と返す。ボタンも待機中の下書きを保存できない。
これは原文の待ち行列を持たず、短い返答が別の質問に誤って結びつくのを避けるため。LLM処理にはタイムアウトを設け、完了時も下書きの世代・TTLを検査する。

DMは `message.id`、ボタンは `interaction.id` で重複排除する。メモリ上の重複排除は再起動を越えないため、永続的な保存の重複防止は上記の冪等キーに任せる。
重複排除・会話状態にはTTLと件数上限を設け、本文・ツールの生出力を含むDiscord SDKの履歴キャッシュも無効化する。

ボタンはGatewayの `INTERACTION_CREATE` で受け、HTTPで3秒以内に初期応答する。保存等が終わらなければ先にdeferし、完了後に更新する。
Gatewayでボタンを受信するため、同じアプリにHTTP受信用のInteractions Endpoint URLを設定しない。
DM本文の受信には `DIRECT_MESSAGES` を使う。BotとのDM本文は `MESSAGE_CONTENT` 特権インテントの例外なので、本機能では同インテントを要求しない。
参照：[Discord Gateway](https://docs.discord.com/developers/events/gateway#message-content-intent)、[Interactionsへの応答](https://docs.discord.com/developers/interactions/receiving-and-responding#interaction-callback)（2026-09-20確認）。

## 受け渡しは DB 経由

対話エージェントからスケジューリングエージェントへ直接渡さない。間に本人の確認が必ず入るため。

```
対話でAを埋める（メモリ）→ 本人がボタンで確認 → PutPreparation で保存
→ スケジューリング側は BuildContext で DB から読むだけ
```

スケジューリング側は対話の存在を知らない。入口が Web でも DM でも完全に同じ。

## Web との併用と競合

会話の開始時に**保存済みの参加条件と `revision` を同じDBスナップショットから読み込む**。
保存時に `expected_revision` を渡し、`revision_conflict` なら下書きと古い確認を破棄して最新版を読み直す。
「開催回の情報が更新されたため、最新の内容で確認し直します」と伝え、訂正は再入力してもらう。古い全項目に新しい版だけを付けて再送しない。
版は他の参加者の操作でも変わるため、原因をWebの更新と断定しない。また、409すべてを競合扱いせず、開催済み・タスク終了等はエラーコードに応じて終了／再選択する。Web側の変更は不要。

## DM が開けないとき

運用上はBotと参加者が共通サーバーに所属し、相手がDMを許可していることを前提とする。実際の送信結果で利用可否を判断し、開けない場合に備えて送り分ける。

| 通知 | 送り先 |
| --- | --- |
| 本人への依頼（`task_requested` / `reminder`） | DM を試す → DM拒否など未送信が確実な失敗だけチャンネルへ（Webリンク付き） |
| 確定の連絡・管理者への差し戻し | チャンネル（全員が知るべき情報のため） |

DM が使えない人は Web だけで完結できる。「DMを必須にしない」という仕様の線は保つ。
429は既存の再試行へ戻し、タイムアウト・5xxなど成否不明の送信は `unknown` として自動退避しない。到達済みのDMとチャンネルへ二重に送るのを避ける。
`notify.Sender` へ通知種別と宛先を渡せるようにする。現状の本文とメンションだけから送り先を推測しない。
チャンネル向け本文には会話の原文・未保存の下書きを含めず、既存の通知情報とWebリンクだけを載せる。

## DM には対象の会の文脈がない

有効な会話があればその対象を維持し、毎ターン未回答タスクから選び直さない。
新規の会話では本人宛ての未回答・期限内の **参加条件確認タスク（`TaskPreparation`）** を対象とし、開催回で重複を除く。1件ならその会。複数ならボタンで選ばせる（LLM不要）。
担当の引き受け・投票・管理者承認は参加条件の保存では完了しないため、MVPではWebリンクへ案内する。
`proposal_id` / `proposal_version` / `task_id` はその案内に使えるが、自然文や参加条件の確認ボタンから提案への同意を作らない。

0件でも自発的な変更はできる必要がある（回答済み・計画確定後の「欠席に変更したい」など）。
0件のときは**本人が所属する変更可能な開催回**をボタンで選ばせる。
`permissions.can_update_preparation` が true の回が対象。
変更可能な回が0件なら、その旨を返して終了する。候補が多ければページ分割し、明示的な対象切替も用意する。
選択前の発言原文は保持せず、対象決定後に再入力を依頼する。選択ボタンも本人と候補集合に束縛し、押下時に所属と変更可能性を再確認する。
参加条件の保存には `PutPreparation` を使い、既存の仕様どおり本人の未回答の参加条件確認も処理する。期限切れタスクへの回答を作らず、開催前の自発的な更新として扱う。

## 予算とクールダウンの置き場所

| | 置き場所 | 理由 |
| --- | --- | --- |
| LLM 呼び出しの上限 | `llm_calls` テーブル（既存・スキーマ変更なし）。**呼び出し前に枠を確保する** | 費用は実損。再起動で消えては困る |
| 空振りカウンタ・クールダウン | メモリ | 再起動で消えてよい |
| 会話のスロット | メモリ・TTL 30分 | 私的な内容を残さないため |

会話の途中で停止したら、次の発言で最初から確認し直す。

### 予算の確保（既存コードの修正を含む）

予算はWeb・DM共通で、**開催回ごとの自由文解釈を最大24枠**に制限する（初期値）。実呼び出し1回に1枠を予約し、1ターンは修復を含め最大2回。
既存カラム `lookup_id` を呼び出し用途の集計キーにも使い、`preparation:<session_id>` という名前空間を設ける。
目次取得の実在するlookup IDと衝突させず、`case_id` には開始時の案件があればそのIDを併記する。案件が未作成でも予約・集計を省略しない。
案件の切替やBot再起動で開催回の予算は回復しない。案件があれば既存の案件総呼び出し数による解釈受付制限も維持する。
計画側の `cases.llm_call_count` には加算せず、計画用の予算を消費しない。この上限は自由文解釈への制限であり、計画・目次取得を含むアプリ全体の費用上限ではない。

いまの `coord.InterpretPreparation` は「件数を数える → トランザクション外で呼ぶ → 事後に記録」で、
同時受信ですり抜け、呼び出し後・記録前の停止で費用が記録されない。**修復の再試行を含む各 `Client.Chat` の直前**に次を行う。

1. トランザクション内で予約済みも含めて件数を数え、1回分が上限内ならIDを決めて `llm_calls` に行を先に作る（モデル名、集計キー、`succeeded=0`、`currency=unknown`、トークンと金額は NULL）。コミットできなければ呼び出さない
2. トランザクションの外で LLM を呼ぶ
3. 結果で同じIDの行を更新する。従来の事後INSERTは行わず二重計上を防ぐ

本MVPの単一プロセス・共有StoreではSQLiteへの接続が1本なので、件数確認と確保を同じトランザクションで直列化できる。複数プロセス対応をこの保証に含めない。
予約後に停止した場合は、実際に呼び出したか分からなくても枠を消費したままにする。費用は不明（NULL）として扱い、`succeeded=0` を「未送信／無料」の証拠にしない。
結果記録は受信リクエストの取消から独立した短い期限の処理で試み、失敗しても予約行は残す。モデル障害の回数も予算から戻さない。

`InterpretRequest` に呼び出し前の予約と呼び出し後の記録を行うフックを設け、解釈器から各試行で呼ぶ。DBと認可はCoordinatorが所有し、Discord層が `Client.Chat` を直接呼ぶ経路は作らない。
`store` に予約IDの更新を足し、用途キーの集計には既存の `CountLLMCallsByLookup` を再利用する。スキーマ変更はない。**Webの自由文解釈にも同じ修正を当てる。** `fake` モードはLLMを呼ばず、費用の予約も作らない。

## 記録するもの

**差分だけ。理由は残さない。**既存の `activity` テーブルに入る。
現在の `submitPreparation` は回答した旨だけを記録し、項目の差分や入口を持たない。
保存前後の正規化済みの値から差分を作り、参加条件の保存と同じトランザクション内で記録する。
入口はプログラムが渡す `web` / `discord` の内部メタデータとし、LLMの引数や公開APIの自由入力には加えない。

```
9/21 15:30  Bさんが参加条件を更新しました（Discord）
              説明の担当：できる → できない
              説明できる時間：40分 → 0分
9/21 15:31  エージェントがCさんに確認を依頼しました
9/21 15:48  計画が確定しました（版2）
```

Discord 側には本人の発言が残るが、そこは管理外である旨を仕様に明記する。
アプリ側は原文を解釈用モデルにのみ送り、会話状態・通知・監査ログへ転記しない。SDKやHTTPのデバッグログにもリクエスト／レスポンス本文を出さない。

## 却下した選択肢

### 会話の履歴を LLM に渡す

injected な文字列が次のターンへ持ち越される。履歴を検証済みの値と未確定項目に絞れば、任意の指示文の持ち越しを減らせる。
ただし型として正しい誤抽出は次のターンに残り得る。検証は本人の意図まで保証しないため、全項目の表示と本人の確認を省略しない。

### 「関係ない話題か」を LLM に判定させる

判定するLLM自体が攻撃対象になる。空振りは検証後の値と未確定項目の変化で測るが、無関係な話が必ず空振りになる保証はない。
`out_of_scope` も案内用の分類であり、認可や予算制限の代わりにはしない。有効な値を交互に変える入力でも費用を制限できるよう、永続的な予算を別に持つ。

### Bot の発話を LLM に書かせる

Bot を踏み台に他人へ文字列を送り込める。次に何を聞くかは「どのスロットが空か」からプログラムが選ぶ。

### 変更理由を自由文でログに残す

私的な理由がDBに入り、「原文を保存しない」という約束と衝突する。差分だけを残す。

### 対話の結果を直接スケジューリングへ渡す

本人の確認を飛ばすことになる。DB を経由し、保存のタイミング＝確認のタイミングにする。

## 実装時の受け入れ条件

- 未登録から「説明できます」→節→時間と回答でき、未確定の仮値を保存しない。「はい」が直前の定型質問に対応する。
- 保存済みの時間だけを変更しても他項目を失わない。「変更なし」も確認でき、参加条件確認タスクを完了できる。
- 部分集合違反・未登録節ID・未知の `unclear`・必須キー欠落・不正な `out_of_scope` を拒否し、矛盾した候補から確認ボタンを出さない。
- 「15分」の確認後に「30分」と訂正した場合、解釈中も完了後も古いボタンで保存できない。別人・別開催回・TTL切れ・再起動後のボタンも保存しない。
- DM連投・処理中のボタン・Gateway再送・二重押下で、下書きの巻き戻りや保存の重複が起きない。
- Webや他の参加者の更新と競合した場合、古い値に新しい版を付けて再送せず、最新値から確認し直す。
- 未回答タスクが0件でも開催前なら更新できる。投票・担当引き受けのタスクは参加条件の保存では回答済みにならない。
- 予算残り1回でWebとDMを同時実行しても、その枠で2回呼ばない。修復試行・案件未作成・予約後の停止でも予算をすり抜けない。
- DM拒否はチャンネルへ退避するが、成否不明時は自動退避しない。ボタンへの初期応答が3秒以内に完了する。
- 保存前のDBには予算記録以外の対話結果が増えず、原文・生のモデル出力はログにも残らない。保存後は差分だけを監査できる。
