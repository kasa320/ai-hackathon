# Discord の常駐Botと対話での参加条件の更新

決定日：2026-09-20。実装ブランチ：`feat/backend-interactive-agent`。
関連：[認証とDiscord連携の方式](auth-and-discord-linking.md)、[自由文の解釈](free-text-interpretation.md)。

## 決めたこと

Discord に常駐Botを置き、**DMでの対話から参加条件を更新できる**ようにする。安全性は次の3つで確保する。

1. **対話エージェントにできるのは、規定された変数の値を決めることだけ。** 文章も、保存も、他人の値も触れない。
2. **会話の記憶は検証済みの変数だけ。** 発言の履歴をLLMに渡さない。
3. **保存は本人のボタン押下でのみ。** 会話は一度も書き込まない。

Webからの入力・修正はこれまで通り使える。DMはWebの代わりではなく、同じ変数へのもう一つの入口。

## エージェント間で共有する変数

### A. 対話エージェントが値を決めてよい変数

ツールの引数のすべて。LLM が世界に対してできるのはこれだけ。

| 変数 | 型 | 再検証（プログラム） |
| --- | --- | --- |
| `attendance` | `attending` \| `absent` | 列挙値のみ |
| `willing_to_present` | bool | — |
| `prepared_section_ids` | 節IDの配列 | 登録済みの節IDのみ |
| `explainable_section_ids` | 節IDの配列 | `prepared` の部分集合 |
| `max_presentation_minutes` | int | 0〜持ち時間 |
| `unclear` | 上の項目名の配列 | 上の5つの名前のみ |
| `needs_followup` | bool | — |
| `out_of_scope` | `null` \| `schedule_change` \| `partial_attendance` \| `other_member` | 列挙値のみ。**何も解除しない** |

上5つは既存の `reading.PreparationSchema()` と同一。対話用のスキーマは作らない。

### B. プログラムだけが決める変数（LLM に見せない・書かせない）

| 変数 | 出どころ |
| --- | --- |
| `member_id` | `message.author.id` → `users.discord_user_id` → `members` |
| `session_id` | 未回答タスクの解決、またはボタンの `custom_id` |
| `expected_revision` | 会話開始時に読んだ `session.revision` |
| `proposal_id` / `proposal_version` / `task_id` | タスクの値 |
| `decision` | ボタンの `custom_id` |

「Cさんの分も登録して」と書かれても `member_id` は発言者から機械的に決まるため影響しない。

### C. 会話の進行にだけ使う変数（メモリのみ・保存しない）

`slots`（Aの現在値）、`unclear`、`misses`（空振り回数）、`cooldown_until`、`expires_at`（TTL 30分）。

LLM が毎ターン見るのは **Aのスキーマ・Aの現在値・今回の1発言** の3つだけ。

## 1ターンの流れ

```
DM 受信
 ├ message.id で重複排除（Gateway は再送しうる）
 ├ 送信者 → member を解決（本人以外は触れない）
 ├ クールダウン中／LLM予算超過 → 定型文で Web へ誘導（LLMを呼ばない）
 ├ LLM に渡すのは A のスキーマ・A の現在値・今回の1発言だけ
 ├ 返るのは record_preparation の引数だけ（文章は返させない）
 ├ ValidatePreparation で再検証（既存）
 ├ out_of_scope が返った → 扱えない旨を定型文で答える（空振りに数える）
 ├ スロットが動かなかった → 空振り +1。3回でクールダウン10分
 └ 動いた → 残った unclear から次の質問を選ぶ（定型文）
          → 全部埋まった → 確認メッセージ＋ボタン
```

**Bot の発話はすべてプログラムが作る定型文。**LLM に文章を書かせないので、Bot を経由して他人へ文字列を送り込む経路がない。

読み取り（「いまの予定を教えて」）は LLM を使わず、保存済みの計画を定型文で返す。

## 受け渡しは DB 経由

対話エージェントからスケジューリングエージェントへ直接渡さない。間に本人の確認が必ず入るため。

```
対話でAを埋める（メモリ）→ 本人がボタンで確認 → PutPreparation で保存
→ スケジューリング側は BuildContext で DB から読むだけ
```

スケジューリング側は対話の存在を知らない。入口が Web でも DM でも完全に同じ。

## Web との併用と競合

会話の開始時に**保存済みの参加条件をスロットへ読み込み**、その時点の `revision` を保持する。ボタン押下時に `expected_revision` を付けて送り、409 なら「Webで更新されたため読み直した」と伝えて確認をやり直す。Web 側の変更は不要。

## DM が開けないとき

Bot から DM を開くには共通サーバー所属と相手の DM 許可が要る。開けない場合に備えて送り分ける。

| 通知 | 送り先 |
| --- | --- |
| 本人への依頼（`task_requested` / `reminder`） | DM を試す → 失敗したらチャンネル（Webリンク付き） |
| 確定の連絡・管理者への差し戻し | チャンネル（全員が知るべき情報のため） |

DM が使えない人は Web だけで完結できる。「DMを必須にしない」という仕様の線は保つ。

## DM には対象の会の文脈がない

未回答の依頼が1件ならその会。複数ならボタンで選ばせる（LLM不要）。0件なら「答えることはありません」と現在の計画を返す。

## 予算とクールダウンの置き場所

| | 置き場所 | 理由 |
| --- | --- | --- |
| LLM 呼び出しの上限 | `llm_calls` テーブル（既存・スキーマ変更なし） | 費用は実損。再起動で消えては困る |
| 空振りカウンタ・クールダウン | メモリ | 再起動で消えてよい |
| 会話のスロット | メモリ・TTL 30分 | 私的な内容を残さないため |

会話の途中で停止したら、次の発言で最初から確認し直す。

## 記録するもの

**差分だけ。理由は残さない。**既存の `activity` テーブルに入る。

```
9/21 15:30  Bさんが参加条件を更新しました（Discord）
              説明の担当：できる → できない
              説明できる時間：40分 → 0分
9/21 15:31  エージェントがCさんに確認を依頼しました
9/21 15:48  計画が確定しました（版2）
```

Discord 側には本人の発言が残るが、そこは管理外である旨を仕様に明記する。

## 却下した選択肢

### 会話の履歴を LLM に渡す

injected な文字列が次のターンへ持ち越される。履歴の代わりに**検証済みのスロット**を渡せば、1ターンの汚染が次に残らない。

### 「関係ない話題か」を LLM に判定させる

判定する LLM 自体が攻撃対象になる。「この Bot にできる唯一のこと（値を埋める）が起きたか」という構造で測る。無関係な話は定義上すべて空振りになる。

### Bot の発話を LLM に書かせる

Bot を踏み台に他人へ文字列を送り込める。次に何を聞くかは「どのスロットが空か」からプログラムが選ぶ。

### 変更理由を自由文でログに残す

私的な理由がDBに入り、「原文を保存しない」という約束と衝突する。差分だけを残す。

### 対話の結果を直接スケジューリングへ渡す

本人の確認を飛ばすことになる。DB を経由し、保存のタイミング＝確認のタイミングにする。

## 残る確認事項

| 項目 | 内容 |
| --- | --- |
| DM の本文取得 | 特権インテントなしで届く想定だが未確認。駄目なら Developer Portal で MESSAGE CONTENT INTENT を有効化する（100サーバー未満なら自己申請で可） |
| 他人に関わる依頼 | 「代わりに誰かに頼んで」は現設計では弾かれる（`out_of_scope: other_member`）。管理者だけ別経路を用意するかは未決 |
| 空振りの閾値 | 3回・10分は初期値。実際に触って調整する |
| 提出までの時間 | 提出期限は 9/22 15:00。中心フローの完成と評価を優先し、間に合わなければこの機能は入れない |
