# バックエンドの実装順と開発エージェント分担案

更新：2026-09-19。追加実装はまだ開始しない。この資料は作業順と分担の提案であり、エージェントもまだ起動していない。

## 現在地

既存のサーバー・SQLite接続・時計に加え、Playbook契約、輪読用の型と未実装メソッド、起動時登録、一覧APIの変更がある。これを `feat/backend-playbook-scaffold` に分けてコミットする。

輪読の業務処理、状態遷移、同意・権限、LLM、通知はこれから。フロントはファイル配置のみとし、今回のバックエンド開発範囲には含めない。

## 実装順

| 順番 | 作るもの | 完了条件 |
| --- | --- | --- |
| 1 | API・共通型・保存境界の契約 | 開催回、メンバー、参加条件、変更案と版、引き受け、投票、イベント、通知待ちの型とエラーを決める。Playbookへの入力不足を補い、各担当が同じ契約で作業できる |
| 2 | DBと共通の調整処理 | 案の作成・回答・本人の引き受け・投票・確定を保存し、最新版・必要条件を検証。計画確定と通知待ち登録を同じトランザクションで行う |
| 3 | 輪読ルールと認証済みAPI | 輪読の入力・範囲・時間・代役制約・承認条件を実装。本人・所属・権限を確認したAPIで、LLMなしでも変更案を確定できる |
| 4 | イベント処理・待機・再開 | 返信・期限で処理が再開し、催促上限、二重送信、再起動、旧版への同意を扱える。仮の判断処理で一連の流れを通す |
| 5 | LLMとDiscordの接続 | 単一モデルで次のツールを選び、Playbookの検証と共通の権限制約を経て実行。呼び出し・費用上限を設定し、通知の失敗・成否不明を区別する |
| 6 | 統合評価と提出準備 | 固定評価ケースを実行し、成功・安全停止・費用を記録。過去のLINE事例と再現比較し、実演用データと手順を用意する |

手順1で契約を揃えた後は、手順2の共通処理、手順3の輪読ルール、認証・API・通知アダプターを並行して進める。実モデルとDiscordの接続可否は早期に少量で確認し、実際の自律実行への接続は制約とイベント処理が整ってから行う。

## 開発エージェントの構成案

統合担当1＋実装担当3の計4エージェントを基本とする。サービス内の実行エージェントを4つに増やすという意味ではない。

| 担当 | 所有する主な場所 | 作業 |
| --- | --- | --- |
| 統合・設計担当 | `cmd/server/`、共通契約、`agent/`、`.agent/decisions/` | 最初に契約を揃え、依存関係の組み立てとLLMループを担当。差分の統合・全体検証を行う |
| 共通処理・DB担当 | `coord/` の実装、`store/`、イベント処理 | 状態遷移、同意と版の検証、永続化、重複防止、通知待ち登録、再起動からの再開 |
| 輪読担当 | `playbook/reading/` | 輪読データ、判断材料、計画検証、承認条件、用途固有のテスト |
| API・外部連携担当 | `api/`、`auth/`、`notify/` | API、セッション・所属検証、Discord送信、外部障害の扱い |

`coord/model.go`・`coord/playbook.go` 等の共通契約は並行作業中に各担当が独自変更しない。変更案を統合担当へ集め、契約の更新を共有してから利用側を直す。DBスキーマは共通処理・DB担当が所有し、API担当や輪読担当は必要な変更を依頼する。

輪読担当の実装が終わったら評価・レビューへ切り替え、他担当の共通制御を独立に検証する。契約確定前に全員が同じファイルを編集する進め方は避ける。

## ブランチと統合

- フロントの構成と設計資料は `master` に置く。既存バックエンド変更は `feat/backend-playbook-scaffold` に分離する。
- 並行実装を開始する際は、契約を揃えたコミットを共通の起点にする。必要に応じて担当ごとのworktreeと `feat/backend-core`、`feat/backend-reading`、`feat/backend-adapters` を使う。
- 同じ作業ディレクトリで複数エージェントがブランチを切り替えない。分離したworktreeを使わない場合は、担当ファイルを固定し、Git操作は統合担当だけが行う。
- 各変更は担当範囲の検証を終えてから統合し、統合後に一連の流れを確認する。`master` へのマージやリモートへのpushは、別途指示があるまで行わない。

評価内容は [evaluation.md](evaluation.md)、用途分離の方針は [architecture.md](architecture.md)、業務要件は [spec.md](spec.md) を参照する。
