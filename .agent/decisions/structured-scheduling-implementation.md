# 構造化した日程調整の実装契約

2026-09-21。ユーザーから入力境界・全員参加方針の実装を依頼された。
既存の公開APIを拡張する補足契約。`docs/` の更新停止中のため本書で追加項目を管理する。

## 対象・デモ・評価

- 対象：固定の幹事がいない既存の輪読グループ。
- 単一デモ：期間で1回を登録 → Web／Discordで本人の参加可能時間と準備を入力 → 自由文は構造化下書きの本人確認 → 全員の共通時間で案を作成 → Discord／Webで全員が参加可能と明示し、管理者・担当者も承認 → 保存・通知。不成立は条件の再入力または管理者判断へ。
- 外部連携：既存のDiscord Bot・OAuth・OrcaRouterのみ。カレンダーや会場予約は追加しない。
- 承認：自由文抽出は下書きのみ。日程案への全員の同意、管理者承認、本人の担当引き受けをアプリが検証する。未回答を可とせず、欠席者を対象から除外して確定しない。
- 成功指標：共通時間以外・未回答・古い案・代理回答では確定しない。原文・任意項目が計画側へ流れない。DiscordとWebで同じ条件を保存・回答できる。既存フローの回帰テストが通る。人の操作数の実測は別途必要。
- スコープ：既存の1開催回の調整と入力境界。期間全体の複数回生成・運営方針の先行承認・会場予約は別の拡張。

## 追加の公開型

`ReadingPreparationData.schedule?`：省略／nullは予定未回答。日時未定の回は、この値が揃うまで日時を提案しない。既存の日時指定済みの回では任意。

```ts
type ScheduleAvailability = {
  status: "provided" | "unknown" | "unavailable";
  weekly_windows: { weekday: number; start: string; end: string }[];
  date_windows: { date: string; start: string; end: string }[];
  max_duration_minutes: number;
};
```

- 曜日は日曜0〜土曜6。時刻はJSTの `HH:mm`、同日内でstart < end、終端のみ24:00可。
- 日付は `YYYY-MM-DD`。個別日付の時間帯はその日の週間設定を置き換える。
- `unavailable_dates` は既存のまま保持し、すべての参加可能時間に優先する。
- providedは時間帯が1件以上、最大参加時間1〜480分。unknown／unavailableは時間帯空・最大参加時間0。
- 各配列は60件まで。同じ日の重複・隣接時間帯は候補計算時に結合する。
- 抽出結果のunclearに `schedule` と `unavailable_dates` を追加。未言及の保存済み条件は保持する。
- `ApprovalProgress.kind` に `all` を追加。required_countは開催回の全対象者数。全員参加の初回日時案で使用する。
- エンドポイントの追加はしない。準備保存・解釈・タスク回答の既存契約を使う。
- 日時未定の回答収集・再計画は期間末を基準に期限を確保する。案への回答期限は提案した日時を基準にする。`starts_at` は案作成時にも仮の提案日時へ更新されるが、`schedule_status=proposed` の間は確定日時として表示しない。
- 候補は共通時間の先頭から30分刻みで列挙する。否決された開始日時は同じ案件で再提案しない。
- 期間から調整した回は確定後も全員参加を維持する。欠席・時間条件の変更で全員参加できなくなれば停止して再調整を案内する。確定済み日時を変更するAPIは既存仕様どおり未対応で、新しい開催回を登録する。日時を直接指定して登録した既存会は従来の再計画ルールを維持する。

## 判断の理由

自由文の要約を計画へ転送する方式は採らない。列挙値・数値・日付・許可IDを厳密に検証しても抽出誤りは残るため、保存前の本人確認を維持する。アプリが操作者・対象・版を束縛し、承認をLLMに抽出させない。

日時は参加可能時間の共通部分から計算し、AI出力も同じ条件で検証する。合わない場合に欠席者を除いて多数決で進める方式は採らない。所要時間や終了期間を自動で書き換えず、不成立理由と見直す条件を提示する。
