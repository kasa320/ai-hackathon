## 確定

| 項目 | 決定 | 理由・却下案 |
| --- | --- | --- |
| 題材 | 輪読運営エージェント。「共通の調整コア＋用途別プレイブック」構成で、輪読プレイブックを実装、会議プレイブックは構想のみ | 汎用の日程調整は既存サービスが多く、独創性と AI の必然性が弱い。却下：汎用サービスとして作る |
| スコープ | ① 立ち上げ（要望→参加確認→日程→担当・準備指示）→ ② 運営中の変更（辞退→代役→範囲の組み直し→同意→反映）→ ③ 当日進行（進行表どおりの通知→進捗記録→次回範囲へ反映）の順に実装 | ③ の結果が次回計画に戻り、運営が一周する |
| 切り捨て線 | 9/21 12:00 に ② が未完了なら ③ をやめ、品質の仕上げに回す | 合計 30〜40h に対して計画が重い |
| 接点 | 予定管理と回答は Web。Discord は通知のみ（ボタンでの即答は余力があれば） | 輪読の実運用で Discord を使っている。却下：LINE（HTTPS の Webhook と友だち追加が必須で、無料枠に送信上限がある。上限は未確認） |
| 認証 | Discord OAuth | 回答者の本人確認と Discord ID の紐付けを一度に行える |
| 技術 | バックエンド：Go（huma v2 / openai-go / sqlc + modernc.org/sqlite）。フロント：JavaScript（フレームワークは友人が選ぶ）。境界は OpenAPI | Go は状態遷移・並行処理・型安全の面で有利。Python の利点（スキーマ自動生成など）は小さい。却下：Node.js で統一、Python |
| LLM | OrcaRouter（OpenAI 互換）。ツール呼び出しループは自前で実装 | 審査のコスト・自律性の説明に使う |
| 分担 | kasa：API・DB・状態遷移・エージェント・評価・費用計測。友人：画面すべて・OAuth・Discord 通知 | 各自の経験（組み込み／IoT、Web）に合わせる |

## 提案中（未確定）

- **調整案件の状態**：情報収集中 → 案作成中 → 同意待ち（案の版 N）→ 反映中 → 確定。自動で解決できない場合は主催者判断待ちへ。イベント駆動で、待機中は LLM を呼ばない。1 起動あたりのツール呼び出しは最大 8 回。
- **開催回の状態**：計画中 → 確定 → 進行中 → 終了。
- **委任ルールの初期値**：AI が単独でできるのは、確認の送信（催促は 1 人 1 回まで）と進行時間の ±5 分の調整。担当の引き受けは本人の同意、範囲の変更は参加予定者の過半数による明示的な同意、日時・中止・初回計画は主催者の承認が必要。回答期限は 24h。
- **コードで禁止すること**：未回答を同意扱いにする、代理同意、古い版への同意での確定、同じ人を 3 回連続で代役にする、私的事情の原文を共有用モデルに渡す、案件ごとの費用・呼び出し回数の上限超過。
