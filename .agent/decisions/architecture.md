# 用途別Playbookの構成

更新：2026-09-19。今回の対象は輪読のみ。会議用の機能・画面・デモは作らない。

## 方針

用途別処理をGoの通常のパッケージで実装し、`coord.Playbook` を通して共通側へ渡す。アプリ内部のプラグインとして起動時に静的登録し、用途を追加するときは再ビルドする。動的ロード、外部プラグインの配布、用途ごとの別サービスは対象外。

共通側の `coord`・`agent` は `playbook/reading` を直接importしない。具体的な用途を選んで登録するのは `cmd/server`。HTTPの入口や通知処理にも輪読専用の条件分岐を散らさない。

## ディレクトリ

```text
src/backend/
├── cmd/server/main.go           # 起動時の依存関係の組み立てとPlaybook登録
└── internal/
    ├── coord/
    │   ├── model.go            # 用途共通の状態・版付き案・承認条件
    │   ├── playbook.go         # 用途別処理のインターフェース
    │   └── service.go          # 用途の登録・解決、将来の調整処理の入口
    ├── playbook/reading/
    │   ├── model.go            # 本・節・準備状況・輪読計画
    │   ├── playbook.go         # インターフェース実装と判断材料の構築
    │   ├── rules.go            # 輪読固有の計画検証・承認条件
    │   └── prompt.go           # 輪読向けの判断指示
    ├── agent/                  # LLM・ツール実行ループ
    ├── api/                    # HTTP入出力と認証済み操作の受付
    ├── store/                  # DBアクセス
    ├── notify/                 # 外部通知
    ├── auth/                   # 本人確認・セッション
    └── clock/                  # 時刻とデモ用時計

src/frontend/js/
├── api.js                      # 既存のAPI呼び出し
├── index.js                    # 既存の起動処理
├── components/health.js         # 共通部品の配置用（コメントのみ）
└── features/
    ├── index.js                # 用途別画面の登録場所（コメントのみ）
    └── reading/index.js        # 輪読固有画面の配置用（コメントのみ）
```

フロントは既存のヘルスチェック表示を維持し、新しい画面やAPI呼び出しは追加しない。バックエンドの上記雛形・登録処理は `feat/backend-playbook-scaffold` に分ける。`master` にバックエンドの変更が入ったことは意味しない。

## 共通と用途別の境界

| 共通側の責務 | 輪読側の責務 |
| --- | --- |
| 案件・案の版・回答・同意の保存 | 本・節・進捗・準備状況の型 |
| 返信・期限をきっかけとする再開 | 復習・範囲縮小などの判断指示 |
| 本人・所属・操作権限・版の検証 | 登録された節や担当可能範囲との整合性検証 |
| 指定された承認条件を満たすかの検証 | 過半数や担当者の引き受けなど、変更ごとの必要条件の算出 |
| 通知待ち・再試行・実行上限・費用 | 未消化範囲の扱いと代役の偏りの制約 |

Playbookは判断材料と条件を返し、同意記録の作成やDB確定・外部通知を直接実行しない。用途側から条件を受け取っても、共通側は対象者の所属・条件の妥当性を確認する。本人確認・旧版拒否・予算上限を用途側が迂回できるAPIは用意しない。

## Playbookの契約

| メソッド | 役割 |
| --- | --- |
| `Descriptor` | 用途IDと表示名 |
| `BuildContext` | 確認済みの共有可能な状態からAIの判断材料を構築 |
| `Instructions` | 用途ごとの判断指示 |
| `ValidatePlan` | 提案された計画の用途固有の制約を検証 |
| `ApprovalRequirements` | その案に必要な投票・承認・本人の引き受け条件を返す |

`Snapshot.Data` と `Proposal.Data` の具体的な型は用途側が持つ。共通側は節ID等の輪読固有項目を解釈しない。これらは内部契約の雛形であり、DB設計の確定版ではない。公開APIは [api.md](api.md) を正とし、内部型との変換をAPI層で行う。開催日時・参加者・持ち時間・履歴等の内部入力は業務実装前に補う。

本・節の保存処理は将来 `store/reading.go` 等にまとめ、共通の案件・同意の処理から区別する。テーブルを一つの汎用JSONに押し込む設計は前提としない。共有するDB接続・トランザクションと用途別のデータ型を分ける。

## 現時点で動く範囲

バックエンドの雛形ブランチでは、輪読の登録、IDによる解決、`GET /api/playbooks` での登録一覧取得を追加している。重複IDと未知のIDは拒否する。一覧取得は公開可能なID・表示名のみであり、案件データを返さない。

輪読の文脈構築・計画検証・承認条件の算出は `coord.ErrNotImplemented` を返す。未実装を「検証成功」「承認不要」と扱わない。再計画、DB保存、同意管理、LLM接続、認証、Discord送信は未完成。追加実装は開始指示を待つ。

## 後から用途を追加する手順

1. `playbook/<用途>/` に用途固有の型・指示・検証・承認条件を実装する。
2. `coord.Playbook` を満たし、既存の共通側のコードを変更せず登録・解決できることを確認する。
3. 必要な保存処理と `features/<用途>/` の画面を追加する。
4. 起動処理とフロントの用途登録へ追加する。複数用途の選択UIはこの時点で設計する。
5. 共通の本人確認・同意・版管理の検証を再利用し、用途固有の評価ケースを追加する。

同じ調整フローに収まらない用途では共通側の拡張も必要になる。「任意の用途を設定だけで追加できる」とは説明しない。
