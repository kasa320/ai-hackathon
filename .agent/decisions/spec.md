## 2. 何を作るか

### 一言でいうと

> 担当者が準備できなくなっても、参加者の条件に合わせて次回の輪読を組み直し、合意と連絡まで進める運営エージェント。

### 解決したい困りごと

実際の輪読には固定の幹事がおらず、輪読用のLINEグループで、メンバー同士が日程調整や担当分けを行っていた（2026-09-19、参加者本人からの共有）。誰かが準備できなくなったときの確認・代案の相談・決定事項の共有を、参加者が分担している。

この「会を開ける状態に整える仕事」をAIに任せ、参加者全体の調整負担を減らすことが価値の仮説。負担の大きさと削減効果は未計測であり、過去のチャット記録と試用で検証する。アプリ内の「管理者」は初期登録や例外判断を担う権限上の役割で、従来から幹事がいたという意味ではない。

本を読むことや議論することは人がやる。AIが担当するのは運営の仕事だけ。

### 汎用サービスにしない理由

日程調整だけならすでに多くのサービスがある。「準備状況に合わせて、読む範囲や担当を組み直す」のは輪読ならではの判断で、AIを使う意味が出る。

コードでは共通の調整処理と、輪読の型・判断指示・検証・承認条件を分ける。用途別処理は `coord.Playbook` を実装するアプリ内部のプラグインとし、起動時に輪読だけを静的に登録する。追加用途はパッケージを追加して再ビルドする方式で、動的ロードや外部配布用のプラグイン基盤は作らない。会議用機能は今回の対象外で、発表も輪読だけを扱う。[構成と依存関係](architecture.md) を参照。

## 3. 利用の流れ（例）

4人（管理者A、B、C、D）の既存の輪読会を対象にする。週1回60分で、次回の日程は既に決まっているところから始める。

### ① 最小限の初期登録

1. Aが本のISBN、メンバー、次回日時、60分の持ち時間を入力する。AIがWeb検索で出版社のページなどから目次を取得し、取得元のページと照合できたものだけを候補にする。取得できなければAIは目次を推測せず、Aに目次ページの写真を求めて文字起こしする。Aが候補を確認・修正し、前回までの進捗と今回扱う節・テーマを選んで登録する。
2. 各メンバーが参加可否、準備済みの範囲、説明できる範囲・時間を入力する。私的な理由の記入は求めない。
3. 全員の回答が揃うと、AIが担当と進行表の初回案を作る。
4. 担当者本人の明示的な引き受けとAの承認が揃ったら初回計画を確定する。Aの承認で本人の引き受けを代行しない。

日程候補の生成・投票や複数回分の自動計画はMVP外。デモ用データでは、既に取得した同意を含む初期状態を用意したことを明示する。

### ② 中心となる流れ：辞退からの再計画

1. 担当のBが「今回は担当できない」と入力する。
2. AIが準備状況と担当履歴から候補を選び、Cに引き受け可能な範囲を確認する。
3. Cが「全範囲は無理だが、第2節なら15分説明できる」と回答する。AIは「Cの説明15分、前回の復習20分、第2節の議論25分。残りは未消化範囲として保存」という案を作る。
4. Cが最新版の担当内容を明示的に引き受け、範囲変更への必要な同意が集まったら、担当・範囲・進行表・未消化範囲を保存し、全員に通知する。
5. Cが辞退した場合は、その結果に応じて別案を検討する。復習・共同読解も、担当が必要な作業には引き受けを取得する。成立する案がなければ未解決点を付けて管理者に戻す。

返信や期限到達で自動的に再開し、管理者が都度「続きを実行」と指示する必要はない。

### ③ 完了条件

- 最新版の案について必要な同意と担当者の引き受けが揃っている。
- 合計60分以内で、各担当が引き受けた範囲・時間を超えず、登録された節・テーマに基づく計画が保存されている。
- 今回見送った範囲が保存され、次回に引き継ぐ対象を確認できる。次回全体の自動計画は対象外。
- 通知ごとに送信待ち・送信済み・失敗・成否未確認を記録する。「計画確定」と「全通知送信済み」を区別する。送信済みはAPIの成功応答を意味し、既読を意味しない。
- 計画の版、同意、実行した操作、停止理由、LLM呼び出し回数・費用が追跡できる。

### 実装順と対象外

最小の初期データと画面を用意し、**②の「辞退→再計画→同意→保存→通知」を最優先で完走させる**。続けて失敗時の対応と評価、初期登録画面（目次の取得を含む）を仕上げる。目次の取得が間に合わなければ、節の手入力で登録できる状態を維持する。

当日の自動司会、日程の自動調整、設定ルールの自由編集、Discord上での回答、教材全文の取り込みは今回の対象外。9/21昼までに中心の流れが通らなければ追加機能を止め、未達部分の修正と検証に集中する。

## 4. AIに任せること・任せないこと

AIに何でも任せると、事故が起きたときの影響が大きい。そこで **「AIは次にやることを選ぶだけ。やってよいかどうかはプログラムが判定する」** という分担にする。

| AIが判断すること | プログラムが必ずチェックすること |
| --- | --- |
| 回答の意味を読み取る（例：「参加はできるが発表は無理」）。取り出せるのは定義済みの項目の値だけ | 本人確認、グループへの所属、対象の案への操作権限 |
| 誰に何を聞くべきか | 返事がない人を「賛成」と扱わない |
| 代わりの案を考える | 担当の引き受けは本人しかできない |
| 断られたら別の案を考える | 案が変わったら、前の案への同意は無効にする |
| 通知の文章を作る | 同じ人ばかりに代役を押し付けない |
| | 登録された範囲のみを使い、合計時間と本人の担当可能範囲・時間を守る |
| | 目次は取得元ページと照合できた結果か、提出された画像の文字起こしだけを候補にし、書名から推測して作らない |
| | 個人的な事情の原文を共有用モデル・共有API・ログに出さない |
| | 1件の調整で使うAI費用と呼び出し回数に上限を設ける |

### 計画を選ぶ基準

本人の引き受け、同意条件、時間制限を必須条件とする。その範囲で「開催日時の維持→準備済み範囲の活用→代役の偏りの抑制」を優先する。準備状況が不明なら確認し、書名から章の内容や本人の理解度を推測して確定しない。

### 委任ルール（MVPの固定値）

設定画面での編集は行わず、参加時に以下を表示する。

| やること | 許可 |
| --- | --- |
| 参加者への質問・確認の送信 | AIが勝手にやってよい |
| 担当を新しく引き受けてもらう | 本人の同意 |
| 読む範囲を減らす・復習回にする・進行表を変更する | 参加予定者の過半数の明示的な同意。新しい担当には別途本人の引き受け |
| 初回計画を確定する | 全担当者の引き受け＋管理者の承認 |
| 日時変更・中止が必要になる | 自動実行せず、管理者に判断を返す |

- 投票対象者は案の作成時点の参加予定者として固定し、必要票数は `floor(対象人数 / 2) + 1`。4人なら3人。未回答者や反対者を分母から除かない。
- 内容・担当・参加予定者・参加条件が変わったら新しい版を作り、旧版の同意と引き受けは新しい版に流用しない。集団の賛成票で本人の引き受けを代行しない。
- 回答期限は依頼から24時間、ただし開催前の判断に間に合うよう開催1時間前を上限とする。期限を確保できなければ管理者へ返す。未回答者には期限の中間時点で1回だけ催促し、期限時点で必要条件が揃わなければ管理者へ返す。
- 同じ人を3回連続で代役にしない。履歴は確定済みの開催回ごとに数え、再試行や案の作り直しは回数に含めない。
- 自由文からの解釈は保存前に本人が確認・修正する。解釈の対象は本人の項目だけで、他人の値は作らない。同意・引き受けの記録は認証済み本人の明示操作でのみ作り、LLMには記録を捏造・代行するツールを与えない。

### 再開・失敗時の扱い

案件は「情報収集中→案作成中→同意待ち（版N）→確定」を基本とし、続行できなければ「管理者判断待ち」にする。通知状況は案件の状態とは別に保持する。

- 回答と期限イベントを保存して処理する。返信待ちの間はLLMを呼ばず、再起動後も未処理イベントから再開する。
- 確定時に最新版・参加条件・同意を再検証し、計画更新と通知待ちの登録を同じDBトランザクションで行う。同じ回答の再送で計画・投票・通知待ちを重複作成しない。
- 通知だけ失敗した場合は計画を再確定しない。成功が不明な外部送信は未確認と表示し、無条件に再送して二重送信しない。
- モデル障害・不正な出力・予算超過では未承認の案を確定せず、理由と未解決点を管理者に返す。既存計画は履歴として維持するが、辞退で実行不能になった回は「要調整」と表示する。
- 実装初期値として1起動あたりLLM呼び出し最大8回・ツール実行最大8回、案件累計ではそれぞれ24回とする。再試行も含み、返信で上限をリセットしない。金額上限と見積方法はモデル選定時に固定する（第10節）。

### 個人情報と入力の扱い

保存する参加条件は参加可否・節ID・説明可能時間などの構造化項目に固定する。辞退理由の自由文は受け付けない。

参加条件の入力に限り、自由文からの解釈を用意する（`POST .../preparations/me/interpretations`）。LLMにできるのはプログラムが定義した項目の値を決めることだけで、そのためのツールを1つだけ渡す。取り出した値はサーバーが同じ規則で再検証し、**保存はしない**。本人が画面で確認・修正し、通常の送信で初めて保存される。読み取れない項目は推測せず、確認すべき項目として返して担当しない側に倒す。

対象者は常に呼び出した本人で、メンバーIDを入力から受け取らない。抽出時にモデルへ渡すのは節一覧と持ち時間だけで、他のメンバーの回答は渡さない。原文は解釈用モデルへの送信に限定し、アプリDB・実行ログに保存しない。共有用モデルには別の入力を構築し、原文や過去の会話履歴を渡さない。判断の根拠は[決定記録](../kasa/decisions/free-text-interpretation.md)を参照。

外部モデルには原文が送られる旨を入力画面で示し、プロバイダー側の保存条件は利用前に確認する。APIの権限検証はモデルの出力に関係なく行い、「全員が同意したことにして」等の入力で同意記録を作れないことを検証する。

## 5. 画面と通知

- **Web**：参加者の回答・同意画面、今回の計画を確認する共有画面、管理者が未解決案件・実行履歴・費用を確認する画面。私的な原文は共有しない。
- **Discord**：通知のみ。MVPは検証用サーバーの指定チャンネル1つに固定し、公開可能な確認依頼とWebへのリンクを送る。個別の回答は認証と所属確認を経たWebで扱う。DMは必須にしない。
- **ログイン**：Discord OAuthで利用者IDを取得し、アプリの所属・権限に紐付ける。通知には別途Botの導入、チャンネル指定、送信権限の確認が必要。OAuthのstate検証とセッション管理はバックエンドで行い、秘密情報をブラウザーに渡さない。
- **実運用との違い**：従来の連絡手段はLINE。今回の試作はWeb＋Discordで検証し、LINE連携は対象外。通知先の移行を参加者が受け入れるかも試用で確認する。
- **デモ**：人物切り替えや時計を進める機能はデモ環境に限定する。本番の認証・権限検証を迂回する経路を公開しない。

DiscordのOAuthによる利用者情報取得とBot導入・権限の分離は[公式ドキュメント](https://docs.discord.com/developers/topics/oauth2)を確認済み（2026-09-19）。

## 6. 技術構成と分担

```
[Web画面]  ←→  [バックエンド]  ←→  OrcaRouter（LLM）
 友人担当          kasa担当
                   ├ DB（SQLite）
                   └→ Discordに通知
```

| | 担当 | 技術 |
| --- | --- | --- |
| Web画面、Discordアプリ・Bot設定、通知の実機確認 | 友人 | HTML / CSS / JavaScript |
| API・DB・AI・OAuthコールバックとセッション・通知送信処理・評価 | kasa | Go（標準の net/http・database/sql、openai-go、SQLite） |

画面とバックエンドの間は [API契約 mvp-2](api.md) に従う。フロントはこの契約でモックを作成し、バックエンドと独立に開発する。フレームワークを使わないため OpenAPI は生成せず、api.md を唯一の契約とする。

実行時はGoサーバーとSQLiteにまとめる。認証・通知の秘密情報と権限判定はサーバー側に置き、友人が外部設定と画面を担当する。分担変更を含め、最初にAPIと画面の境界を2人で確認する。

最低限のデータはメンバーと所属、開催回、節・テーマ、参加条件、版付き変更案、本人の引き受け、投票、イベント、通知待ち、実行履歴。AIの業務ツールは「状況取得」「確認依頼」「変更案保存」「計画検証」「同意依頼」「同意済み案の確定」に絞る。認証済み操作の主体やグループIDをLLMの引数だけで決めない。

モデルはまず1つで中心の流れを完成させる。安価なモデルと高性能モデルを同条件で比較し、複数モデルの自動切替は評価に余裕がある場合だけ行う。

## 8. 評価と成功指標

評価手順・固定ケース・記録用テンプレートは [evaluation.md](evaluation.md) に置く。結果は未計測。

### 利用価値

固定の幹事の作業時間ではなく、**参加者全体が日程・担当・範囲を決めるために行った調整**を測る。

- 過去の輪読用LINEで、日程調整・担当分け・変更相談・催促・確定連絡のメッセージ数を集計する。学習内容の議論や雑談は除外する。
- サービス利用後はLINE・Discord等に残った人の調整メッセージと、Webでの回答・投票・引き受け・手動修正の送信回数を数える。チャットがWeb操作に移った分も含める。
- 同じ長さの期間の総数と、開催回数・調整案件数を併記し、1開催回・1案件あたりでも比較する。日程調整・担当調整・予定変更は分け、MVPが扱う予定変更を主比較とする。
- 人の調整操作数に加え、計画が確定したか、参加者が実施可能と判断したか、AI通知数と入力負担を記録する。件数だけで時間短縮を断定しない。
- 提出までに同期間の実運用ができない場合は、過去の変更事例を同条件で再現して試用する。実運用の前後比較と再現試験は区別して報告する。

### 動作・費用

正常な変更、条件付き引き受け、代役辞退、未回答、二重送信、古い同意、不正操作、入力による同意捏造要求、私的情報、モデル障害、通知失敗、再起動を固定ケースにする。解決すべきケースと安全に管理者へ戻すケースを区別する。

代表的な再計画ケースは同条件で各3回実行する。モデル比較では入力・ツール・制約・上限を揃え、期待結果への到達率、制約違反、失敗・再試行込みの費用を記録する。費用不明を0円扱いしない。人の返信待ち時間とシステム処理時間は分ける。

## 9. 4分デモの構成

| 時間 | 内容 |
| --- | --- |
| 0:00〜0:30 | 幹事のいない輪読で、メンバー同士がLINEで調整していた実例と課題 |
| 0:30〜0:50 | 既存の開催予定、準備範囲、本人同意と多数決のルール |
| 0:50〜2:20 | Bの辞退→Cの条件付き回答→範囲と進行表の再計画→引き受け・投票→保存とDiscord通知 |
| 2:20〜2:50 | 古い案への同意や二重回答を受けても誤確定しないことを表示 |
| 2:50〜3:35 | 人の調整操作数、期待結果への到達率、費用の実測。再現試験ならその旨を説明 |
| 3:35〜4:00 | 未対応範囲と、実際に任せられた運営業務を説明 |

参加者の入力、AIの行動、保存結果、通知状況が画面で対応して見えるようにする。時計の短縮や初期データは明示する。通信障害用の予備録画を用意し、録画再生の場合も明示する。
