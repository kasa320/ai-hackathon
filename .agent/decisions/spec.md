## 2. 何を作るか

### 一言でいうと

> 「この本を、この人たちと輪読したい」と伝えるだけで、AIが参加者と連絡を取り、日程・担当・準備内容を決め、途中で欠席などが出ても計画を組み直し、当日の進行まで面倒を見る。

### 解決したい困りごと

輪読の幹事は、参加者への連絡、日程の調整、担当の割り振りを毎回自分で行っている。誰かが準備できなくなるたびに、代わりの担当を探したり範囲を変えたりする。この「会を開ける状態に整える仕事」をAIに任せる。

本を読むことや議論することは人がやる。AIが担当するのは運営の仕事だけ。

### 汎用サービスにしない理由

日程調整だけならすでに多くのサービスがある。「準備状況に合わせて、読む範囲や担当を組み直す」のは輪読ならではの判断で、AIを使う意味が出る。

ただし、将来ほかの用途（社内の会議など）にも使えるよう、中身は次の二層に分けて作る。

- **共通部分（調整コア）**：連絡する、回答を集める、同意を取る、確定する、通知する。
- **用途ごとの部分（プレイブック）**：何を決めるか、どんなルールで決めるか。
  - 今回実装するのは **輪読プレイブック**。
  - **会議プレイブック** は発表で構想として紹介するだけ。

## 3. 利用の流れ（例）

4人（主催者A、B、C、D）で技術書を週1回、1回60分で読む場合を例にする。

### ① 立ち上げ

1. Aが Web 画面で、本・メンバー・頻度を入力する。
2. AIが Discord で B・C・D に参加確認と都合のよい日時の入力を依頼する。回答は Web 画面で行う。
3. AIが日程と各回の担当の案を作る。
4. Aが承認すると確定し、全員に「初回の範囲と準備してほしいこと」を通知する。

### ② 途中で予定が崩れたとき

1. 担当のBが「今回は担当できない」と入力する。
2. AIがCに「代わりに担当できますか？」と確認する。
3. Cも断った場合、AIは別の案を考える。例：「範囲を半分にして、前回の復習の時間をとる」。
4. 範囲を変えるにはメンバーの同意が必要なので、AIが同意を集める。
5. 同意が揃ったら、担当・範囲・進行表を更新して全員に通知する。

### ③ 当日

1. 進行表に沿って、AIが Discord に「次はCさんの発表（15分）です」などと流す。
2. 終わったら、どこまで読めたかを入力する。
3. 読み残しがあれば、AIが次回の範囲に組み込む。これで ① の計画に戻り、運営が一周する。

**実装の順番は ① → ② → ③。** 9/21 の昼までに ② が終わっていなければ、③ はあきらめて、それまでの部分の品質を上げる。

## 4. AIに任せること・任せないこと

AIに何でも任せると、事故が起きたときの影響が大きい。そこで **「AIは次にやることを選ぶだけ。やってよいかどうかはプログラムが判定する」** という分担にする。

| AIが判断すること | プログラムが必ずチェックすること |
| --- | --- |
| 回答の意味を読み取る（例：「参加はできるが発表は無理」） | 操作している人が本人かどうか |
| 誰に何を聞くべきか | 返事がない人を「賛成」と扱わない |
| 代わりの案を考える | 担当の引き受けは本人しかできない |
| 断られたら別の案を考える | 案が変わったら、前の案への同意は無効にする |
| 通知の文章を作る | 同じ人ばかりに代役を押し付けない |
| | 個人的な事情の原文を、共有用の文章づくりに使わない |
| | 1件の調整で使うAI費用と呼び出し回数に上限を設ける |

### 誰の許可がいるか（委任ルール）※初期値は未確定

主催者が画面で変更できる設定にする。

| やること | 許可 |
| --- | --- |
| 参加者への質問・確認の送信 | AIが勝手にやってよい |
| 当日の進行時間の小さな調整 | AIが勝手にやってよい |
| 担当を新しく引き受けてもらう | 本人の同意 |
| 読む範囲を減らす・復習回にする | メンバーの同意 |
| 日時を決める・変える・中止する | 主催者の承認 |

## 5. 画面と通知

- **Web**：予定の確認、回答、同意、主催者の設定など、操作はすべて Web で行う。
- **Discord**：通知だけ。「確認をお願いします」＋Webへのリンクや、当日の進行アナウンス。ボタンで即答する機能は余裕があれば追加する。
- **ログイン**：Discordアカウントでログインする。なりすましを防げ、Discordへの通知先も自動で分かる。
- LINE は見送る。公開サーバーや友だち追加が必要で、無料で送れる数にも上限がある（上限の数字は未確認）。

## 6. 技術構成と分担

```
[Web画面]  ←→  [バックエンド]  ←→  OrcaRouter（LLM）
 友人担当          kasa担当
                   ├ DB（SQLite）
                   └→ Discordに通知
```

| | 担当 | 技術 |
| --- | --- | --- |
| Web画面・ログイン・Discord通知 | 友人 | JavaScript（フレームワークは友人が選ぶ） |
| API・DB・AIの処理・評価 | kasa | Go（huma v2、openai-go、sqlc、SQLite） |

画面とバックエンドの間は、API の仕様書（OpenAPI）で取り決める。バックエンドのコードから自動で作られる。

Go を選んだ理由：状態の管理や並行処理、型によるミス防止に向いている。Python の方が楽な点（スキーマの自動生成など）もあるが、差は小さい。
