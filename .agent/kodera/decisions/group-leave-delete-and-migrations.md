# グループ脱退・削除・DB変更の方針

更新日: 2026-09-21  
対象ブランチ: `feat/member-leave`

## 背景と解決したい問題

現状は、一般メンバーが参加中のグループから自分で脱退する手段と、管理者が不要になったグループを削除する手段がない。そのため、参加状態が実態とずれたまま残り、今後の候補日時、回答依頼、予定調整、画面上の閲覧権限にも退会済みユーザーが含まれ続ける。

今回、参加関係に脱退日時、グループに削除日時を持たせる。レコードそのものを消さずに現在有効かどうかを判定できるため、過去の開催記録を残しながら、脱退者や削除済みグループを今後の処理と通常画面から除外できる。

## 決定事項

### メンバーの脱退

- 一般メンバーは自分自身をグループから脱退させられる。
- 管理者は脱退できない。グループを離す必要がある場合はグループ削除を使う。
- 開催中の回がある間は脱退できない。
  - 「開催中」は、確定済みの回について `開始日時 <= 現在 < 開始日時 + 所要時間` の範囲とする。
- 脱退後も過去の履歴は残り、残ったメンバーは閲覧できる。
- 脱退した本人は、脱退後そのグループ、回、課題、履歴を閲覧できない。
- 開始前の予定回では脱退者を欠席扱いにし、残ったメンバーで再調整する。
- 脱退によって不要になった本人向けの未処理タスクと通知は終了させる。
- 脱退通知は、脱退者を除く現在のメンバーそれぞれの Discord 個人チャットへ送る。

### グループ削除

- 管理者だけがグループを削除できる。
- 誤操作防止は、管理者限定と影響を明記した確認ダイアログで行う。グループ名の完全一致入力は求めない。
- 開催中の回がある間は削除できない。
- 削除は論理削除とし、グループと過去履歴のデータは内部に保持する。
- 削除後はメンバー全員がグループ、回、課題、履歴を通常の API と画面から閲覧できない。
- グループに属する未処理タスク、イベント、通常通知、調整案、目次取得処理を終了させる。
- 削除通知は、削除直前の管理者を含む全メンバーそれぞれの Discord 個人チャットへ送る。

### Discord 通知

- 既存の回答依頼、リマインド、予定確定などの通知方法は変更しない。
- 今回追加する脱退通知とグループ削除通知だけは個人 DM 専用とし、DM が失敗しても共通チャンネルへフォールバックしない。
- 各受信者の送信状態を個別に保存し、一部の DM 失敗が脱退・削除そのものを取り消さないようにする。

### その他の境界条件

- 管理者1人だけのグループは存続できる。
- 新しい回の作成には、現在有効なメンバーが2人以上必要。
- 再加入、管理者交代、削除済みグループの復元、通知再送専用画面は今回の対象外。
- 同じ冪等性キーによる脱退・削除の再送は、最初と同じ成功結果を返せるようにする。

## 実装方針

### データベース

- `groups.deleted_at` を追加し、値があるグループを削除済みとして扱う。
- `members.left_at` を追加し、値がある参加関係を脱退済みとして扱う。
- 脱退・削除通知専用の `group_notifications` を追加し、受信者単位で送信状態を管理する。
- 未送信の既存通知を終了できるように `cancelled` 状態を追加する。

### バックエンド

- `POST /api/groups/{group_id}/leave` を追加する。
- `DELETE /api/groups/{group_id}` を追加する。
- 権限、開催中、冪等性をサーバー側で検証する。
- 一覧・詳細・準備対象・バックグラウンド処理から脱退済みメンバーと削除済みグループを除外する。
- 開始前の回は脱退者を欠席にして入力版数を更新し、強制的に再調整する。
- ライフサイクル通知を個人 DM 専用キューから配信する。

### UI

- グループ画面に、一般メンバーには「グループを脱退」、管理者には「グループを削除」を表示する。
- 脱退前に影響を説明する確認ダイアログを表示する。
- 削除時は影響を明記した確認ダイアログを表示する。グループ名の入力は求めない。
- 開催中は操作を無効化し、理由を表示する。最終判定はサーバー側でも行う。
- ダイアログはキーボード操作、フォーカス復帰、読み上げ用ラベルとエラー通知に対応する。

## マイグレーションを今回後回しにする理由

現在は保存すべき本番データがまだなく、既存 DB を作り直せる。今の段階では、既存データを壊さず新しい設計へ移す手順を管理するマイグレーション基盤より、確定前のスキーマを直接更新して検証する方が単純である。

マイグレーションが必要になるのは、実データを残したまま DB の形を変える段階である。導入すると、変更を番号付きの手順として共有でき、開発・検証・本番で同じ順序を再現でき、誰の DB がどの状態か分からなくなる問題を防げる。Go では `pressly/goose/v3` を第一候補とするが、DB 設計が固まり実データ投入前になるまで追加しない。

## 2026-09-21: ローカル環境（`.env`）の設定を戻した

`http://localhost:24680` が開けなくなった件の原因と対処。

- 原因は2つ。サーバープロセスが停止していたことと、`.env` の `ADDR` が `:8080` に変わっていたこと。既定は `:24680` のため、起動しても 24680 では開けない状態だった。
- 加えて `PUBLIC_BASE_URL` は未設定で既定の `http://localhost:24680` のままだった。`AllowedOrigins` は `PUBLIC_BASE_URL` から作るため、8080 で配信した画面からの更新系リクエストは Origin 検証で `403 forbidden` になる。ポートを変えるなら両方を揃える必要がある。
- ユーザーの判断で 24680 に戻した。`.env` を `.trash/env-20260921-1716/` へ退避したうえで、`ADDR=:24680`、`DISCORD_REDIRECT_URL=http://localhost:24680/api/auth/callback` に変更した。Discord Developer Portal 側のリダイレクトURL登録も 24680 に合わせる必要がある。
- `DISCORD_CLIENT_SECRET` と `SESSION_SECRET` が空のため Discord ログインは無効（`discord_login=false`）。ユーザーの判断で `DEV_MODE=1` を追加し、デモ帯の人物切り替え（`/api/dev/login`）で画面を確認する方針にした。`SESSION_SECRET` が空の間は一時的な署名鍵になり、再起動のたびにログアウトされる。
- 最新コードで `bin/server` を再ビルドして起動し、`/api/health` が 200・`dev_mode: true`、トップページと `/api/dev/status` が 200 であることを確認した。

### 競合と解決

- 競合したのは `src/frontend/js/ui.js` の `createDialog` だけ。両ブランチが同じ関数を別の目的で書き換えていた。
  - こちら（脱退・削除）：`aria-labelledby` 用の `titleId`、エラー欄の `id` と `aria-live="assertive"`、フォーカス復帰の厳密化、入力欄が無いダイアログでの送信ボタンへのフォーカス。
  - 向こう（日程調整）：`pending` による二重送信の防止、`setPending` による入力欄の一括無効化と送信中ラベル、送信中の Esc 取り消しの抑止、`onSubmit` の await と失敗時のエラー表示。
- どちらも残す形で統合した。片方を選ぶとアクセシビリティか二重送信対策のどちらかが失われるため。戻り値は `{ dialog, close, showError, showReceipt, setPending, errorId }` とした。
