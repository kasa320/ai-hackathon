# 参加条件スキーマの配列上限を Gemini が扱える大きさに下げる

更新日: 2026-09-21
対象ブランチ: `feat/member-leave`

## 背景と解決したい問題

自由文から参加条件を取り出す処理（`LLMInterpreter`）が、Gemini 系モデルで高確率に失敗していた。症状は HTTP 500「解釈に失敗しました」で、Web からも Discord の DM からも同じ。

原因は [`PreparationSchema()`](../../../src/backend/internal/playbook/reading/interpret.go) が返す JSON Schema の配列上限だった。Gemini は構造化出力を制約付きデコードで実現しており、スキーマを状態機械へ変換する。`maxItems` は「いま何件出したか」を数える状態を要求し、それが要素側の状態と掛け算になる。3つの配列がいずれも `maxItems: 60` だったため状態数が上限を超え、次のエラーで拒否されていた。

```
The specified schema produces a constraint that has too many states for serving.
Typical causes are schemas with long array length limits (especially when nested),
or schemas using complex value matchers (for example, integers with min/max).
```

この不具合は、計画側（`PlanSchema`）には出ない。解釈側だけが大きな配列を3つ持っていた。

## 決定事項

- `llm_calls` ではなくスキーマ側を直す。配列の `maxItems` を実測で通る大きさに下げる。

| 項目 | 変更前 | 変更後 | 根拠 |
| --- | --- | --- | --- |
| `weekly_windows` | 60 | **21** | 7曜日 × 1日3枠。これを超える入力は現実的に起きない |
| `date_windows` | 60 | **14** | 特定日の指定。調整期間は数週間なので足りる |
| `unavailable_dates` | 60 | **21** | 終日参加できない日。同上 |

- `minimum` / `maximum` / `pattern` は**変更しない**。実測でサイズだけが効くと分かったため、触る理由がない。
- `"type":["object","null"]` も**変更しない**。原因と確定していないうえ、`null` を返すモデルを壊す可能性がある。
- サーバー側の検証（60件まで許可）は変更しない。AI 経由で入らない分は Web のフォームから登録できる。
- 値の根拠をコード内のコメントに残す。数字の意味が分からないまま 60 に戻されるのを防ぐため。

## 実装方針

変更は `PreparationSchema()` の3か所の数値のみ。保存されるデータの形、API の契約、DB のスキーマは変わらない。変わるのは「モデルに渡す出力形式の指示」だけで、保存前の検証は [`ValidatePartialPreparation`](../../../src/backend/internal/playbook/reading/interpret.go) が従来どおり行う。

## 検証記録

2026-09-21。すべて `gemini-2.5-flash-lite` に対する実測。

### しきい値の特定

最初の計測は同じスキーマを連続で投げたため、**1回目の成否がキャッシュ経由で残り4回に伝播**し、実質1試行になっていた。この誤りに気づき、毎回異なるスキーマを投げる方式へ組み直した（サイズを交互に回し、時間帯の混雑が特定サイズへ偏らないようにした）。

| 3つの配列の `maxItems` | 成功 | 失敗 | 失敗率 |
| --- | --- | --- | --- |
| 10 | 6 | 0 | 0% |
| **21** | **6** | **0** | **0%** |
| 40 | 1 | 5 | 83% |
| **60（変更前）** | 1 | 5 | **83%** |

40 と 60 の成功1回はいずれも1.5秒台で、キャッシュに当たった回。コンパイルが走った呼び出しはすべて失敗していた。しきい値は 21 と 40 の間にある。

### Gemini 共通の制限であることの確認

flash-lite 固有ではないかを確かめた。

| モデル | `maxItems`=59 | `maxItems`=21 |
| --- | --- | --- |
| `google/gemini-2.5-flash` | **400**（5.9秒） | 200（3.6秒） |
| `google/gemini-2.5-flash-lite` | **400**（74.1秒） | 200（1.6秒） |

`gemini-2.5-flash` も同じく落ちる。**モデルを変えても回避できない**ため、スキーマ側の修正が必要と確定した。

### 修正後の確認

修正したコードからスキーマを読み込み、そのまま各モデルへ投げた。

| モデル | 結果 | 所要 |
| --- | --- | --- |
| `google/gemini-2.5-flash-lite` | ✅ 200 | 1.6秒 |
| `google/gemini-2.5-flash` | ✅ 200 | 4.0秒 |
| `openai/gpt-5-mini` | ✅ 200 | 6.2秒 |
| `anthropic/claude-sonnet-5` | ✅ 200 | 17.4秒 |
| `orcarouter/marunage-extract` | ✅ 200 | 74.5秒 |
| `anthropic/claude-haiku-4.5` | ❌ 503 | 上流の一時障害（この時間帯ずっと継続） |

いずれも正しく `record_preparation` を呼び、時間帯と最大参加時間を抽出できている。

### 自動テスト

- `go build ./...`、`go vet ./...` 成功。
- `go test ./... -count=1` 全パッケージ成功。

## 切り分けの過程で判明した別の問題

### `gemini-2.5-flash-lite` の所要時間が二極化する

スキーマ修正後も、`marunage-extract` 経由の呼び出しが **1.5秒か73秒か**のどちらかになる。中間がない。

```
73.0秒 / 1.5秒 / 3.3秒 / 66.1秒   （4回とも成功、4回とも flash-lite に振られた）
```

README に書いた「Discord の1往復は60秒で打ち切る」を約半分の確率で超える。スキーマとは別の問題として、解釈側のモデル選定で評価する。

### 難易度による振り分けが発火しない

`marunage-extract` はアダプティブゲート戦略だが、E13 相当の難しい入力を投げても**常に弱プール**（flash-lite）に振られた。強プールと Default は一度も使われていない。

レスポンスヘッダーも `by=balanced` のままで、学習が始まっていない。アダプティブ系はトラフィックを学習する方式のため、数十回の試行では収束しない。

フロンティアエスカレーションはルールベースで学習不要だが、[公式ドキュメント](https://docs.orcarouter.ai/routing/frontier-escalation.md)によると発動条件が「連続2ターンが難易度閾値を超える」「短期間に2つの客観的な失敗」であり、**セッション単位**で判定される。解釈は1回の呼び出しで完結し、セッションを紐づけるヘッダーも送っていないため、この条件を満たさない。加えて Rollout の既定はシャドウモード0%で、有効にしても適用されない。

## 評価項目でのアピールポイント

### ③ 信頼性・堅牢性（主）

- モデルごとに構造化出力の受け入れ能力が違うことを実測で把握し、**最も制約の厳しいモデルに合わせてスキーマを設計**した。特定ベンダーに依存しない構成になっている。
- 「モデルを差し替えられる」ことの前提が、API の形だけでなく**スキーマの複雑さ**にもあることを示せる。OrcaRouter で200モデルが使えても、スキーマが重ければ選べるモデルは絞られる。

### ② コストパフォーマンス（副）

- 修正前は Gemini 系（最も安い選択肢）が実質使えなかった。修正により、解釈用途で `gemini-2.5-flash-lite` を候補にできるようになった。

### 計測手法そのもの

- 最初の計測はキャッシュの影響で結論を誤らせるところだった。**同じ入力を連続で投げると独立した試行にならない**ことに気づき、設計を組み直して再計測した。この過程自体が、実測を根拠にする姿勢の裏づけになる。

## 却下した案

### 案1: `minimum` / `maximum` / `pattern` も外す

当初はこれらも原因の候補として外す案だった。実測でサイズだけが効くと分かったため採用しない。制約を外すとモデルが範囲外の値を出しやすくなり、サーバー検証でのやり直しが増える。直す必要のないものは触らない。

### 案2: 解釈に Gemini を使わない

`gemini-2.5-flash` でも同じ 400 が出るため、flash-lite をやめても回避できない。`sonnet-5` や `gpt-5-mini` に限定すれば動くが、**最も安く最も速い選択肢を失う**。また不具合を残したまま「Geminiを選ぶと壊れる」製品になる。

### 案3: 400 を一時的な失敗として再試行する

切り分け前は断続的な失敗に見えたため候補だった。原因がサイズと確定した以上、再試行しても同じスキーマを送るだけで必ず失敗する。加えて 400 には認証エラーなど再試行すべきでないものが含まれる。

### 案4: `maxItems` をもっと小さくする（10など）

10 も 0% の失敗率で通った。しかし `weekly_windows` が10件だと「1日1〜2枠」しか表現できず、利用者の入力を削る可能性が上がる。速度差もない（10 と 21 で所要時間は変わらなかった）ため、通る範囲で大きい 21 を選んだ。

## 後で必ず検討・実装すること

- `gemini-2.5-flash-lite` の所要時間の二極化（1.5秒／73秒）の扱い。解釈側の計測結果を見て、弱プールを `gemini-2.5-flash` へ変えるか判断する。
- `marunage-extract` の強プールと Default が使われていない件。計画側（`marunage-plan`）でも発火しないなら、ルーターの構成そのものを見直す。
- 計画側でエスカレーションを試すなら、`case_id` などでセッションを紐づけるヘッダーを送る必要がある。
- `anthropic/claude-haiku-4.5` の 503 が解消したら、候補として再評価する。
- Web のフォームは60件まで受け付けるが、AI 経由は21件までになった。この差を利用者に説明するかは未決。
