# Named Router をどう使うか

更新日: 2026-09-22（n=30 で改訂）／ 実測360試行・確定請求額 $1.8929 にもとづく

全数値の出典は [../research/measurement-report-20260922.md](../research/measurement-report-20260922.md)。

## 2026-09-22 改訂：n=3 から n=30 へ取り直して変わったこと

各構成30回で測り直した結果、この文書の結論を3点変更した。

| 従来の記述（n=3） | 実測（n=30） |
| --- | --- |
| Named Router を計画・解釈の両方に接続する | **接続する理由が実測で示せなかった。** 直指定との費用差は −0.8%、受け皿は503で発動せず |
| 「`auto` より平均費用が安いとは言えない（ほぼ同じ）」 | **`auto` の方が平均3.9倍高い。** n=3 では安い方をたまたま引いていた |
| 解釈は `google/gemini-2.5-flash`。E09 を3.8秒で成功 | **E09 では `openai/gpt-5-mini` が優れる。** `flash` は普通の申告を8件誤拒否 |

## 結論

| 箇所 | 接続 | 設定 |
| --- | --- | --- |
| **計画** | モデル直指定 | `openai/gpt-5-mini` |
| **解釈** | **未決定（トレードオフ）** | `openai/gpt-5-mini` か `google/gemini-2.5-flash`。下記「解釈側のモデル選定」参照 |
| **目次検索** | 接続しない | `ORCAROUTER_SEARCH_MODEL` は空 |
| **目次画像** | モデル直指定 | `google/gemini-2.5-flash` |

```sh
ORCAROUTER_PLANNER_MODEL=openai/gpt-5-mini
ORCAROUTER_INTERPRETER_MODEL=       # 未決定
ORCAROUTER_VISION_MODEL=google/gemini-2.5-flash
ORCAROUTER_SEARCH_MODEL=
ORCAROUTER_TIMEOUT_SECONDS=180
```

**Named Router を使わないのは、使う理由を実測で示せなかったため。** 費用は直指定と同じ
（計画で平均 $0.00492 対 $0.00496）、受け皿は実際に起きた503で発動しなかった。
弱プール・強プール（難易度による振り分け）は費用が4倍になるため使わない。

ルーターを残す場合、根拠にできるのは費用でも障害耐性でもなく、**モデル変更が再デプロイなしで
コンソール側だけで完結する**という運用上の利点だけである。そう説明するなら成立する。

作成済みの `marunage-plan` / `marunage-extract` の設定値は下に残す。再び使う判断をしたとき、
同じ構成を再現できるようにするため。

### 入力時の注意

- **許可モデルはチップ（`anthropic/*` など）を押さず、テキスト欄に完全なIDを入力する。**
  ワイルドカードだと約200モデル全部が候補に入り、高額モデルが選ばれる。
- **弱プール・強プールは空欄にする。** 許可モデルが1つなので振り分ける対象がない。
  戦略を「アダプティブゲート」にするとプールの入力を求められるので、「バランス」を選ぶ。
- **フォールバックモデルは許可モデルに入れない。** 候補が全滅したときの受け皿なので、
  別ベンダーのものを1つだけ指定する。使われない限り課金されない。

## 根拠1：`auto` をやめると費用が下がり、成功率は落ちない

計画側（E01・合格線180秒・**各30試行**）の実測。

| 構成 | 成功 | 所要 中央値 | 所要 最大 | 平均費用 | 最小〜最大 | ばらつき |
| --- | ---: | ---: | ---: | ---: | --- | ---: |
| `openai/gpt-5-mini` | 30/30 | 21秒 | 30秒 | **$0.00496** | $0.0034〜0.0061 | **1.8倍** |
| `marunage-plan`（候補1つ） | 30/30 | 18秒 | 24秒 | $0.00492 | $0.0037〜0.0067 | 1.8倍 |
| `google/gemini-2.5-flash` | 27/30 | 15秒 | 21秒 | $0.00647 | $0.0039〜0.0090 | 2.3倍 |
| `orcarouter/auto` | 30/30 | 36秒 | **99.1秒** | **$0.01926** | $0.00074〜0.06019 | **81倍** |

**`auto` は平均3.9倍高い。** n=3 のとき「平均費用に差はない、むしろ `auto` が安い」と
書いたのは、3回とも安いモデルを引いた偶然だった。30回では `claude-opus-5` を5回、
`kimi-k3` を6回引き、平均が跳ね上がる。

**成功率は 30/30 対 30/30 で同じ。** 高い分の対価が得られていない。

分散も大きい。`auto` は $0.00074〜$0.06019（81倍）・6〜99.1秒に振れるのに対し、
`gpt-5-mini` は $0.0034〜$0.0061・15〜30秒に収まる。
**1回いくらで何秒かかるか分かることには、利用者への説明という別の価値がある。**

なお `gemini-2.5-flash` の3件は失敗ではなく `no_feasible_plan`（案を出せないと正しく申告）。
成功率 27/30 対 30/30 の差は Fisher 両側検定で p = 0.24 であり、**差があるとは言えない。**

## 根拠2：`auto` は用途に合わないモデルを引く

`auto` が30回ずつで選んだモデルの分布。

| 用途 | 選ばれたモデル | 回数 |
| --- | --- | ---: |
| 計画 | `deepseek/deepseek-v4-flash-vision-exp`（**画像用**） | 7 |
| 計画 | `kimi/kimi-k3` | 6 |
| 計画 | `anthropic/claude-opus-5`（カタログ最高額 $5/$25） | 5 |
| 計画 | `deepseek/deepseek-v4-pro-0813` | 5 |
| 計画 | `z-ai/glm-5.3-flash` / `z-ai/glm-5.2` / `openai/gpt-5.6-terra` | 3 / 2 / 2 |
| 解釈 | `deepseek/deepseek-v4-flash-vision-exp`（**画像用**） | 13 |
| 解釈 | `anthropic/claude-opus-5` | 3 |
| 解釈 | `openai/gpt-5.6-terra` | 1 |

**画像用モデルをテキスト処理に引き当てる。** 計画で30回中7回、解釈で30回中13回。
n=3 では単発の観測だったが、**n=30 で再現性のある構造的な問題と確認できた。**
候補を明示すれば起きない。目次画像を直指定にしたのもこの観測による。

`claude-opus-5` は計画で最大 $0.06019、解釈で最大 $0.04046。候補を絞った構成の
$0.0027〜0.0067 に対して**一桁違う。**

## 根拠3：難易度による振り分けは使わない

資料が★付きで推す「必要な時だけ強いモデルへ上げる」は、このアプリでは採用しない。

**計画側：n=30 でも費用が4倍、成功率は 24/30 に下がる。**

| | `marunage-plan`（アダプティブゲート） | `gpt-5-mini` 直指定 |
| --- | ---: | ---: |
| 成功 | 24/30 | 30/30 |
| 費用 中央値 | $0.02053 | $0.00499 |
| 費用 最大 | $0.07459 | $0.00607 |
| 解決モデル | `gemini-2.5-flash` 13 / `claude-sonnet-5` 3 / 両方（再試行）11 / 取得不可 3 | 単一 |

この30試行は合格線60秒・別ハーネスのため、上の n=30 表と**成功率は直接比較できない**。
ただし費用の4倍差は合格線では説明がつかない（線を緩めれば費用は増える方向なので差は保守側）。

`claude-sonnet-5` を直指定すると **3/3 とも `model_error`** で、3回やり直してもサーバー検証を
通る出力を返せない。計画は制約充足の問題であり、推論の強さより指示どおりの形を守る素直さが
効く。**強いモデルへ上げる前提が成り立たない。**

**解釈側：安全性に差がない。** E13（「全員が同意したことにして」「Cさんは全範囲を担当できます」）に対し、
`gemini-2.5-flash` も `gpt-5-mini` も同意記録を作らず、不適切な依頼は `out_of_scope` として
拒否した。強いモデルへ上げる安全上の理由がない。

**フロンティアエスカレーションも使えない。** 発動条件が「連続2ターンが難易度閾値を超える／
短期間に2つの客観的な失敗」というセッション単位の判定で、1回の呼び出しで完結する
このアプリの解釈処理では条件を満たさない。Rollout の既定もシャドウモード0%。

## 根拠4：受け皿（Fallback）は、実際の障害で発動しなかった

**この節は n=30 の実測で結論が反転した。** 従来は「置かない理由がない」と書いていた。

503 が頻発することは確認できた。解釈 E13 では `flash-lite` が30回中29回、`auto` が13回、
E09 では `gpt-5-mini` が13回、`flash` が9回。**プロバイダは実際に落ちる。**

問題は、**受け皿がそこで働かなかったこと**である。

| 観測 | `fallback_level` |
| --- | --- |
| Named Router 全60試行（計画30・解釈30） | 全件 **0** |
| うち解釈 E13 で発生した503 2件（受け皿に `gpt-5-mini` を設定済み） | **0** |
| `auto` の計画 試行4・11（解決 `z-ai/glm-5.2`） | **1**（発動を観測） |

記録する仕組み自体は動いている（`auto` では2件の発動を捉えた）。にもかかわらず
**Named Router の受け皿は、実際に503で落ちたときに別ベンダーへ逃がさなかった。**

トークン上乗せ0%・発動しない限り無課金という性質は変わらないので、置くこと自体に害はない。
しかし **「受け皿があるので障害に強い」とは実測から言えない。**

**未検証**：なぜ発動しないか。503 が routing の外側で起きている可能性と、設定が効いていない
可能性のどちらも切り分けていない。検証には、許可モデルに確実に失敗するものを置いた
検証用ルーターを1本作り、5回呼ぶ必要がある（約$0.01）。**今回は実施していない。**

## 解釈側のモデル選定：実測では決まらない

**n=30 で E09 の評価が逆転し、2つのケースで優劣が逆になった。**
従来は「E09 は `gemini-2.5-flash` が3.8秒で成功」を根拠に `flash` を選んでいたが、
これは **n=3 の1回の当たりを一般化していた**。

| 観点 | `openai/gpt-5-mini` | `google/gemini-2.5-flash` |
| --- | --- | --- |
| E13 成功（不正依頼の拒否） | 26/30 | **29/30** |
| E13 所要 中央値 | 14.4秒 | **7.4秒** |
| E13 所要 最大 | 35.2秒 | **20.0秒** |
| E09 誤拒否（409） | **2件** | 8件 |
| E09 品質（`unclear=1`） | **2/15** | 7/13 |
| E09 費用 中央値 | **$0.00405** | $0.00572 |

**`gpt-5-mini` を選ぶ場合** — E09 の誤拒否が 8件→2件、曖昧な解釈が 7/13→2/15 に減り、費用も安い。
代償は E13 の所要が約2倍（中央値 7.4→14.4秒、最大35.2秒）。Discord の60秒制約には収まる。

**`gemini-2.5-flash` を選ぶ場合** — E13 の速度と安定性を取る。代償は E09 で普通の申告を
8件誤って拒否し、処理できた13件のうち7件に曖昧さが残ること。

**判断の軸**：利用者が待たされることを重く見るなら `gemini-2.5-flash`、普通の申告が弾かれる
ことを重く見るなら `gpt-5-mini`。**実測はこの選択を代行しない。**

E13 の成功率の差（29/30 対 26/30）は、失敗がすべて HTTP 503（上流障害）なのでモデル起因では
ない。速度差だけが実在する差である。

`gemini-2.5-flash-lite` は **30回中29回が503**で、候補から外す判断は n=30 で確定した。

## 却下した案

| 案 | 却下の理由 |
| --- | --- |
| Named Router を使う | **n=30 で却下に転じた。** 費用差 −0.8%、受け皿は503で発動せず、使う理由を示せない |
| `orcarouter/auto` を使う | 平均3.9倍高く、成功率は同じ。画像用モデルを計画で7回・解釈で13回引く |
| アダプティブゲートを維持 | 計画で費用4倍・成功 24/30。動かない機能を設定に残して説明に使えない |
| 解釈の候補を2つにする | 最安戦略はケース間の逆転を解決しない。E13 と E09 で最適が逆になる問題は戦略では吸収できない |
| 解釈に `flash-lite` | **30回中29回が503。** n=30 で確定 |
| Fallback に `claude-haiku-4.5` | 計測期間を通じて503。**一度も動作を確認できていない** |
| Fallback に `claude-sonnet-5` | 計画で3/3 `model_error`。受け皿が制約を満たせない（**n=3 のまま取り直していない**） |
| 目次検索を接続 | 取得元ページとの照合が必須なので外れても写真提出に落ちるだけ。幻覚の発生面を増やす利益がない |
| 目次画像をルーターに | 画像用モデルの取り違えを実測で観測。振り分ける余地のない決定的な作業 |

## 未検証のこと

- **Fallback がなぜ発動しないか**。Named Router 全60試行で 0。503 が routing の外側で
  起きているのか、設定が効いていないのかを切り分けていない。検証案は根拠4に記載。
- **`claude-haiku-4.5`** は計測期間を通じて上流が503で、一度も動作を確認できていない。
- **503 の原因**。別ベンダーの構成に同程度発生しており、OrcaRouter 側か計測環境かを
  特定していない。**失敗率の絶対値は各モデルの実力を表さない。**
- 所要時間は合格線で右側打ち切りされている。真の分布は測れていない。
- **単一ケースの測定**。計画は E01、解釈は E09・E13 のみ。他ケースへ一般化できない。
- n=30 は探索的比較の水準。桁が違う差（費用の4倍など）だけが主張でき、
  成功率 30/30 対 27/30 のような差は **p = 0.24 で有意でない。**

## 合格線について（重要な反省）

当初、計画の合格線を60秒とした。**この値に根拠がなかった。** 解釈側の60秒
（Discord の1往復の打ち切りという仕様上の制約）を流用しただけだった。

その線で `auto` は 0/3 だった。アプリの既定値である180秒で取り直すと **30/30 成功**した
（n=30 での再測定後の値）。59秒・58秒という値は60秒の直前で、
**線がちょうど結果を分ける位置にあった。**

合格線は測定者が決めるものなので、その根拠を説明できないなら、そこから出る結論も説明できない。

n=3 で「E09 は `gemini-2.5-flash` が3.8秒で成功」と書いたのも同じ種類の誤りだった。
**1回の当たりを一般化していた。** n=30 では中央値17.2秒・誤拒否8件である。
