## 4. 読み取りと注意

### 分かったこと（n=30 で更新）

1. **`orcarouter/auto` は動くが高い。** 計画側は合格線180秒で 30/30 成功する。しかし平均費用は
   $0.01926 で `gpt-5-mini` の3.9倍、費用は $0.00074〜$0.06019（81倍）、所要は6〜99.1秒に振れる。
   **成功率が同じなので、高い分の対価が得られていない。**
2. **`auto` は用途に合わないモデルを引く。** `deepseek/deepseek-v4-flash-vision-exp`（画像用）を
   計画で30回中7回、解釈で30回中13回。`claude-opus-5` を計画5回・解釈3回。
   n=3 では単発の観測だったが、**n=30 で再現性のある構造的な問題と確認できた。**
3. **高いモデルほど良いわけではない**。`claude-sonnet-5` は計画で3/3とも `model_error`。
   3回やり直してもサーバー検証を通る出力を返せなかった（**n=3 のまま取り直していない**）。
4. **計画の難易度振り分けは逆効果**。`marunage-plan`（アダプティブゲート）は n=30 で
   成功 24/30、費用 中央値 $0.02053・最大 $0.07459。`gpt-5-mini` 直指定の4倍である。
5. **解釈の難易度振り分けが「有効」というのは誤りだった。** n=3 で E13 が 3/3 だったのは
   偶然で、この観測は合格線40秒・旧ルーター構成のものである。最終構成での E13 は 28/30、
   E09 は 17/30 だが**誤拒否9件・`unclear=1` が12/17** と品質が低い。
6. **`gemini-2.5-flash-lite` は使えない**。E13 で **30回中29回が503**、成功1回。n=30 で確定した。
7. **Named Router の上乗せは検出できない。** 計画で平均 $0.00492 対 $0.00496（−0.8%）、
   解釈 E13 で中央値 $0.00266 対 $0.00303。**削減もしていない。**
8. **受け皿（Fallback）は発動しなかった。** Named Router 全60試行で `fallback_level` = 0。
   解釈 E13 で503が2件出たときも 0 のままだった。`auto` では2件の発動を観測している。
9. **E09 で `gemini-2.5-flash` の評価が逆転した。** n=3 の「3.8秒で成功」は1回の当たりだった。
   n=30 では所要中央値17.2秒、普通の申告を**8件誤拒否**、成功13件中7件に曖昧さが残る。
   E09 の処理品質は `gpt-5-mini` が明確に上である。

### 数値を読むときの注意

- **所要秒は右側打ち切りされている**。合格線ちょうどの値（20.0 / 40.0 / 240.2）は
  「その値以上」という意味しか持たない。真の分布は測れていない。
  したがって「60秒超が0件」は「超えなかった」ではなく「測っていない」。
- **費用が不明な試行がある**。打ち切られた呼び出しはヘッダーが返らず、`request_id` が取れないため
  確定額を取得できない。0 として扱っていない。
- **第3.1節の試行数は各3回**（`marunage-plan` のみ4回）。断定するには足りない。
  第3.0節は各30回だが、これも**探索的比較の水準**である。成功率 30/30 対 27/30 の差は
  Fisher 両側検定で p = 0.24、Wilson 95%信頼区間も重なり、**差があるとは言えない。**
  桁が違う差（費用の4倍など）だけが主張できる。
- **503 が広範囲に発生している。** n=30 では `flash-lite` 29件、E13 `auto` 13件、
  E09 `gpt-5-mini` 13件、E09 `flash` 9件。別ベンダーの構成に同程度出ているため、
  特定モデルの問題ではなく OrcaRouter 側か計測環境の要因と見られる。
  **失敗率の絶対値は各モデルの実力を表さない。** 使えるのは503を除いた相対差だけである。
- `anthropic/claude-haiku-4.5` は計測期間を通じて上流が 503 を返し続けた。
  記録はモデルの性能ではなく**障害を測っている**。
- 計測器の判定に2件の誤りがあり、修正して取り直した（第8節）。
- **二重起動による汚染を1件検出した。** 2026-09-22 02:18:00〜02:20:24、2つのプロセスが
  同じポートで E13 `auto` を同時に実測していた。該当データは集計から除外し、
  `.worktrees/router-extract/.trash/measurements-contaminated-20260922/` へ退避した（削除していない）。

## 5. 集計とグラフ化の軸

記事で出す図は次の3つを想定する。数値が揃っていない軸は図にしない。

1. **構成別の1案件あたり費用**（棒グラフ）: 構成を横軸、確定$の平均を縦軸。試行数と失敗数を figure の注記に併記する
2. **構成別の所要秒**（棒グラフ）: 資料p12の「auto の最安は最速ではない」を自分のデータで確認する
3. **費用と到達率の関係**（散布図）: 横軸に1案件あたり費用、縦軸に期待結果への到達率。安いだけの構成を選ばない根拠にする

集計時の約束:
- 失敗した試行の費用も分子に含める。成功0件なら「算出不可」と書く
- 実運用と再現試験の数値を1つの平均に混ぜない
- 見積額しか取れなかった構成は「推定」と明記し、確定請求額と同じ図に並べない

## 8. 計測器の誤りと訂正

計測の途中で、判定ロジックに2件の誤りが見つかった。いずれも取り直した。

### 誤り1: E13 の判定がシードの初期値を拾っていた

`SELECT COUNT(*) FROM tasks WHERE decision IS NOT NULL` が 0 より大きいかで判定していたが、
`replan_demo` のシードは確定済み状態を作るために回答済みタスクを3件作る（`devapi/seed.go`）。
**LLM を呼ぶ前から条件を満たしており、解釈が成功しさえすれば「制約違反」になっていた。**

解釈の前後で `tasks`・`preparations`・`proposals` の件数を取り、増えた場合だけ違反とする形に直した。
これで「解釈は何も保存しない」という仕様を正しく検証できる。E09 にも同じ検証がかかる。

### 誤り2: 安全な拒否を失敗に数えていた

モデルが「扱えない依頼」と分類すると、サーバーは `invalid_state`（HTTP 409）で下書きの生成を拒否する
（`coord/interpret.go`）。E13 ではこれが**期待動作**だが、判定は HTTP 200 以外をすべて失敗にしていた。

応答本文を見て、「扱えません」を含む 409 を「安全拒否」として別に数えるよう直した。

### この経験からの教訓

どちらも「失敗が多い」方向の誤りだったため、**実装が悪いという誤った結論に傾きかけた**。
計測器そのものを疑う手順がないと、測った数字がそのまま誤った設計判断につながる。
