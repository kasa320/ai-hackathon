## 4. 読み取りと注意

### 分かったこと

1. **`orcarouter/auto` は計画側では動く（合格線180秒で3/3）。** ただし費用が16倍、所要が5倍に振れる。
   解釈側は20秒以内に返らなかったが、こちらも合格線を上げれば通る可能性がある（未検証）。
   さらに用途に合わないモデルを引く: `deepseek/deepseek-v4-flash-vision-exp`（画像用）、`z-ai/glm-5.2`、
   そして **`anthropic/claude-opus-5`（1回 $0.046776）**。同じ処理を `marunage-extract` は $0.0025〜0.0038 で行った。
2. **高いモデルほど良いわけではない**。`claude-sonnet-5` は計画で3/3とも `model_error`。
   3回やり直してもサーバー検証を通る出力を返せなかった。費用は安いモデルの約14倍。
3. **計画の難易度振り分けは逆効果**。`marunage-plan`（アダプティブゲート）は4試行すべてで
   強プール `claude-sonnet-5` に振り分け、4試行すべて失敗した。
4. **解釈の難易度振り分けは有効に見える**。`marunage-extract` は E13 で強プール `gpt-5-mini` に振り、
   **3/3 期待通り**で最短だった（9.5〜17.7秒）。ただし E09 は 0/3 で、ケースによる差が大きい。
5. **`gemini-2.5-flash-lite` は二極化する**。1.8秒で返る回と、20秒/40秒の打ち切りに達する回に割れ、
   中間の値がない。E13 の最終計測では3/3が503だった。

### 数値を読むときの注意

- **所要秒は右側打ち切りされている**。合格線ちょうどの値（20.0 / 40.0 / 240.2）は
  「その値以上」という意味しか持たない。真の分布は測れていない。
  したがって「60秒超が0件」は「超えなかった」ではなく「測っていない」。
- **費用が不明な試行がある**。打ち切られた呼び出しはヘッダーが返らず、`request_id` が取れないため
  確定額を取得できない。0 として扱っていない。
- **試行数は各3回**（`marunage-plan` のみ4回）。断定するには足りない。
- `anthropic/claude-haiku-4.5` は計測期間を通じて上流が 503 を返し続けた。
  記録はモデルの性能ではなく**障害を測っている**。
- 計測器の判定に2件の誤りがあり、修正して取り直した（第8節）。

## 5. 集計とグラフ化の軸

記事で出す図は次の3つを想定する。数値が揃っていない軸は図にしない。

1. **構成別の1案件あたり費用**（棒グラフ）: 構成を横軸、確定$の平均を縦軸。試行数と失敗数を figure の注記に併記する
2. **構成別の所要秒**（棒グラフ）: 資料p12の「auto の最安は最速ではない」を自分のデータで確認する
3. **費用と到達率の関係**（散布図）: 横軸に1案件あたり費用、縦軸に期待結果への到達率。安いだけの構成を選ばない根拠にする

集計時の約束:
- 失敗した試行の費用も分子に含める。成功0件なら「算出不可」と書く
- 実運用と再現試験の数値を1つの平均に混ぜない
- 見積額しか取れなかった構成は「推定」と明記し、確定請求額と同じ図に並べない

## 8. 計測器の誤りと訂正

計測の途中で、判定ロジックに2件の誤りが見つかった。いずれも取り直した。

### 誤り1: E13 の判定がシードの初期値を拾っていた

`SELECT COUNT(*) FROM tasks WHERE decision IS NOT NULL` が 0 より大きいかで判定していたが、
`replan_demo` のシードは確定済み状態を作るために回答済みタスクを3件作る（`devapi/seed.go`）。
**LLM を呼ぶ前から条件を満たしており、解釈が成功しさえすれば「制約違反」になっていた。**

解釈の前後で `tasks`・`preparations`・`proposals` の件数を取り、増えた場合だけ違反とする形に直した。
これで「解釈は何も保存しない」という仕様を正しく検証できる。E09 にも同じ検証がかかる。

### 誤り2: 安全な拒否を失敗に数えていた

モデルが「扱えない依頼」と分類すると、サーバーは `invalid_state`（HTTP 409）で下書きの生成を拒否する
（`coord/interpret.go`）。E13 ではこれが**期待動作**だが、判定は HTTP 200 以外をすべて失敗にしていた。

応答本文を見て、「扱えません」を含む 409 を「安全拒否」として別に数えるよう直した。

### この経験からの教訓

どちらも「失敗が多い」方向の誤りだったため、**実装が悪いという誤った結論に傾きかけた**。
計測器そのものを疑う手順がないと、測った数字がそのまま誤った設計判断につながる。
